# PUB/SUB Messaging

---

> 개발자가 클라우드에서 고도의 기능과 복잡한 구조의 애플리케이션을 쉽게 구축할 수 있게 해 주는 비동기식 커뮤니케이션 모델.
> 

최신 클라우드 아키텍처에서는 애플리케이션을 서비스라고 불리는 더 작고 독립적인 빌딩 블록으로 분리하는데, 게시/구독 메시징은 이러한 분산 시스템을 위한 즉각적인 이벤트 알림을 제공한다. 이 메시징은 독립적인 소프트웨어 모듈 간의 확장 가능하고 신뢰적인 커뮤니케이션을 지원한다.

## 주요 구성 요소

---

### 메시지

- 발신자로부터 수신자에게 전송되는 통신 데이터.

### 주제

- 모든 메시지에는 관련된 주제가 존재한다. 주제는 보내는 사람과 받는 사람 사이의 중간 채널 역할을 한다. 주제는 해당 주제에 대한 메시지에 관심이 있는 수신자 목록을 유지 관리한다.

### 구독자

- 메시지의 수신자. 구독자는 관심 있는 주제에 구독해야 한다. 메시지를 병렬로 사용하여 다른 작업을 수행할 수 있다.

### 게시자

- 주제에 대한 메시지를 작성하여 해당 주제의 모든 구독자에게 한 번만 전송한다. 게시자와 구독자 간의 상호 작용은 일대일 관계이며, 게시자는 브로드캐스팅 중인 정보를 누가 사용하고 있는지 알 필요가 없으며, 구독자는 메시지의 출처를 알 필요가 없다.

## 주요 기능

---

### 푸시 전송

메시지가 주제에 게시될 때 비동기 이벤트 알림을 즉시 푸시한다. 

### 다중 전송 프로토콜

주제는 메시지 대기열, 서버리스 함수, HTTP 서버, 이메일 주소 등 여러 유형의 엔드포인트에 연결한다.

### 팬아웃

메시지가 주제로 전송된 후 복제되어 여러 엔드포인트로 푸시될 때 발생한다. 팬 아웃은 비동기 이벤트 알림을 제공하여 병렬 처리가 가능하다.

### 필터링

필터링 기능을 사용할 경우 구독자가 메시지 필터링 정책을 생성 가능하다. 이를 통해 해당 주제에 게시된 모든 메시지를 수신하는 것이 아니라, 관심 있는 알림만 수신할 수 있다.

### 멀티플렉싱

경우에 따라 게시자가 구독자가 될 수도 있다. 메시지 스트림을 멀티플렉싱하고, 내부적으로 일관된 방식으로 서로 연결되는 여러 시스템을 만들 수 있다.

## 이점

---

> 게시/구독 모델을 사용하여 [이벤트 기반 아키텍](https://aws.amazon.com/ko/event-driven-architecture/)처를 구축할 수 있다. 또한, 이벤트를 사용하여 분리된 서비스 간 서로 트리거와 통신이 가능하다.
> 

### 폴링 제거

메시지 주제를 사용하면 정보와 업데이트가 푸시 기반으로 즉시 전송되므로, 메시지 소비자가 새로운 정보 및 업데이트를 주기적으로 확인하거나 폴링할 필요가 없다. 따라서 응답 시간이 단축되며, 지연이 허용되지 않는 시스템에서 특히 문제가 될 수 있는 전송 지연 시간이 줄어든다.

### 동적 타겟팅

여러 구독자가 변경되거나 업그레이드 되거나 사라질 수 있으며 그에 따라 시스템이 동적으로 조정된다.

### 분리 및 확장

게시자와 구독자는 분리되어 있으며 서로 독립적으로 작동하므로, 게시자와 구독자를 독립적으로 개발하고 확장 가능하다. 게시/구독 방식에서는 모든 구성 요소가 연동하여 작동하는 방식을 유연하게 조정할 수 있기 때문에, 기능을 추가하거나 변경해도 시스템 전체에 그 파급 효과가 전달되지 않는다.

### 통신 간소화

게시/구독 모델은 메시지 주제에 대한 단일 연결을 사용하고 모든 지점 간 연결을 없앰으로써 복잡성을 줄인다. 주제에서 구독을 관리하여 어떤 메시지를 어떤 엔드포인트로 전송할지 결정한다. 콜백 횟수가 적으므로 결합이 느슨해지고, 코드의 유지 및 관리/확장이 쉬워진다.

### 내구성

게시/구독 메시징 서비스는 여러 서버에 동일한 메시지의 복사본을 저장하여 매우 높은 내구성과 한 번 이상의 전송을 보장하는 경우가 많다.

### 보안

메시지 주제는 콘텐츠를 게시하려는 애플리케이션을 인증하며, 네트워크를 통해 전송 중인 메시지를 암호화된 엔드포인트를 사용하여 보호할 수 있도록 한다.

## 사용처

---

- 병렬 비동기 처리 작업 수행
- 애플리케이션및 시스템 알림 전송
- 비동기 워크플로 관리
- 워크로드 밸런싱
- 여러 시스템에 로깅
- 복제에 팬아웃 사용
- 서버리스 애플리케이션 조정
- IoT 데이터 스트리밍

# 도메인 주도 설계

---

## [DDD란?](https://ko.wikipedia.org/wiki/%EB%8F%84%EB%A9%94%EC%9D%B8_%EC%A3%BC%EB%8F%84_%EC%84%A4%EA%B3%84)

> 도메인 패턴을 중심에 두어, 해당 도메인에 맞게 소프트웨어를 모델링하는 설계 접근 방식이다.
> 

소프트웨어를 만들 때, 실제 업무나 문제 영역(도메인)을 깊이 이해하고 그에 맞게 프로그램을 설계하는 방식으로, 도메인의 전문가와 개발자가 함꼐 협력하여 비즈니스 로직과 규칙을 코드에 잘 반영하도록 만드는 것이다. 

## 특징

- 소프트웨어 코드는 실제 비즈니스 용어를 그대로 사용하여 구현된다. 예를 들어 대출 신청 프로그램 같은 경우, 'LoanApplication'(대출 신청서)이나 'Customer'(고객) 같은 클래스와 'AcceptOffer'(제안 수락) 또는 'Withdraw'(철회) 같은 메소드를 사용해, 코드를 비즈니스 상황과 자연스럽게 연결시킨다. **이를 언어 통일(Ubiquitious Language)라고 한다.**
- 도메인 그 자체와 도메인 로직에 초점을 맞춘다. 일반적으로 많이 사용하는 **데이터 중심의 접근법**을 탈피해서 순수한 도메인의 모델과 로직에 집중한다. 즉, 비즈니스 로직과 도메인 모델을 중심으로 시스템을 설계한다.
- [소프트웨어 엔티티와 도메인 컨셉을 가능한 일치시킨다. 분석 모델과 설계, 코드가 다른 구조가 아니라 도메인 모델부터 코드까지 항상 함께 움직이는 구조의 모델을 지향하는 것이 DDD의 핵심 원리이다.](https://incheol-jung.gitbook.io/docs/q-and-a/architecture/ddd#undefined-12)
- 도메인 전문가와 개발자 간 지속적으로 협력하며 모델을 개선하고 발전시킨다.

## 적용 상황

1. 도메인 복잡성이 높은 경우
    - 비즈니스 규칙과 로직이 복잡하고 다양한 비즈니스 용어 및 프로세스가 존재하는 경우
    - 도메인 전문가의 지식과 경험이 프로젝트 성공에 결정적인 영향을 미치는 경우
2. 비즈니스 로직이 핵심 경쟁력인 경우
    - 애플리케이션의 주요 가치가 단순한 CRUD(생성, 조회, 수정, 삭제) 이상의 복잡한 비즈니스 로직에 기반할 때
    - 도메인 모델을 통해 비즈니스 문제를 해결하는 것이 경쟁력 강화에 기여하는 경우
3. **지속적인 도메인 지식 공유와 협력이 필요한 경우**
    - 개발팀과 도메인 전문가(비즈니스 측)가 긴밀하게 협력하여 도메인 모델을 지속적으로 개선해야 하는 상황
    - 팀 내 공통 언어(Ubiquitous Language)를 통해 소통 효율성을 높일 필요가 있을 때
4. **도메인의 변화가 빈번한 경우**
    - 비즈니스 요구사항이나 시장 변화에 따라 도메인 로직 및 규칙이 자주 변할 가능성이 있는 경우
    - 모델의 확장성과 유지보수를 고려하여 설계가 중요한 경우
5. **대규모 시스템 또는 분산 시스템의 경우**
    - 시스템이 여러 모듈(혹은 Bounded Context)로 구성되어 있으며, 각 모듈 간의 경계와 통신을 명확히 할 필요가 있을 때
    - 시스템 복잡도를 낮추고, 각 도메인의 자율성을 보장하며, 일관성을 유지하는 것이 중요한 경우

### 추가 고려 사항

- **직의 역량**: DDD를 효과적으로 적용하려면 팀원들이 도메인 지식을 깊게 이해하고, 도메인 전문가와의 소통이 원활해야 한다.
- **프로젝트 규모**: 도메인의 복잡성이 낮거나 프로젝트 규모가 작을 경우 DDD의 도입이 오히려 불필요한 복잡성을 초래할 수 있다.
- **비즈니스 요구사항의 명확성**: 도메인 모델링의 핵심은 비즈니스 요구사항을 정확하게 파악하는 것이므로, 초기 요구사항 분석 단계에서 충분한 시간과 노력이 필요하다.

## 구분

### 전략적 설계 Strategic Design

- **목표:**
    
    > 전체 시스템의 큰 그림을 그리며, 도메인을 여러 부분으로 나누어 각 부분이 명확한 경계를 갖도록 하는 것이다.
    > 
- **주요 개념:**
    - **Bounded Context:**
    하나의 도메인이 여러 의미로 해석될 수 있을 때, 각기 다른 해석이나 모델을 분리하는 경계이다. 예를 들어, "고객"이라는 개념이 영업, 고객지원, 마케팅 등에서 다르게 사용될 수 있는데, 이때 각각의 영역(컨텍스트)으로 나누어 관리한다.
    - **Context Mapping:**
    여러 Bounded Context 간에 어떻게 소통하고 협력할 것인지 그 관계와 통신 방법을 정의한다.
    - **Subdomain 분류:**
    도메인을 핵심 도메인(Core Domain), 지원 도메인(Supporting Domain), 일반 도메인(Generic Domain)으로 구분하여, 각 도메인이 가진 중요도와 역할을 명확하게 한다.
    
    <aside>
    
    전략적 설계는 회사나 시스템의 전체적인 구조를 잡고, 각 팀이나 부서가 어떤 역할을 해야 하는지 큰 틀에서 정리하는 것과 비슷하다. 전체 조직도를 만들고, 각 부서의 역할과 책임을 분명히 하는 것이라고 할 수 있다.
    
    즉, 시스템 전체의 큰 그림과 도메인 간의 경계, 관계를 정의하는 단계로, '어떤 부문(컨텍스트)들이 존재하는가?'와 '각 부문은 어떻게 연결되어 있는가?'를 다룬다.
    
    </aside>
    

### 전술적 설계 Tactical Design

- **목표:**
    
    > 전략적 설계에서 정해진 도메인 경계 내에서, 실제 코드로 구현할 수 있는 도메인 모델을 만드는 데 집중한다.
    > 
- **주요 개념:**
    - **엔티티 (Entity):**
    고유한 식별자를 가지고 있으며, 시간이 지나도 본질이 유지되는 객체이다. 예를 들어, 특정 고객의 정보는 그 고객 고유의 ID를 통해 식별할 수 있다.
    - **값 객체 (Value Object):**
    고유 식별자가 없으며, 값 자체로 의미가 있는 객체이다. 예를 들어, 주소나 날짜처럼 변경 불가능한 데이터를 표현할 때 사용된다.
    - **애그리거트 (Aggregate)와 애그리거트 루트 (Aggregate Root):**
    관련 객체들을 하나의 단위로 묶어 일관성을 유지하기 위한 경계이다. 애그리거트 루트는 이 단위 내에서 중심 역할을 하며, 외부에서는 오직 루트를 통해서만 접근한다.
    - **도메인 서비스 (Domain Service):**
    특정 엔티티에 속하지 않는 비즈니스 로직을 캡슐화한다. 예를 들어, 여러 엔티티에 걸쳐서 처리해야 하는 복잡한 업무 규칙을 수행할 때 사용된다.
    - **리포지토리 (Repository):**
    도메인 객체들을 저장하고 불러오는 역할을 한다. 데이터베이스 접근 등의 영속성 관련 작업을 담당한다.
    - **팩토리 (Factory):**
    복잡한 객체 생성을 담당하여, 객체 생성 로직을 한 곳에 모아 관리한다.
    
    <aside>
    
    전술적 설계는 실제 소프트웨어 개발에서 쓰이는 도구와 같은 역할이다. 예를 들어, 건물을 짓기 전에 설계도를 그리는 전략적 설계가 있다면, 전술적 설계는 그 설계도를 바탕으로 실제 벽돌, 창문, 문 등을 구체적으로 만드는 공정이라고 할 수 있다.
    
    즉, 전략적 설계 내에서 실제 비즈니스 로직을 구현하는 방법론으로, 객체, 서비스, 데이터 접근 등 구체적인 코드 설계 방식을 다룬다.
    
    </aside>
    

## 주의 사항

- **도메인 복잡성 판단:**
    
    DDD는 복잡한 도메인 문제를 해결하는 데 강점을 발휘하지만, 도메인이 단순하거나 비즈니스 로직이 복잡하지 않다면 오히려 과도한 설계가 될 수 있다.
    
- **도메인 지식의 충분한 확보:**
    
    도메인 전문가와의 긴밀한 협력이 필수. 도메인에 대한 깊은 이해가 없다면 모델이 실제 비즈니스 요구를 제대로 반영하지 못할 수 있다.
    
- **조직 및 팀의 역량:**
    
    DDD를 성공적으로 적용하려면 팀 전체가 도메인 주도 설계의 원칙과 개념을 잘 이해해야 한다. 팀원 간의 공통 언어(Ubiquitous Language)를 정립하고 이를 지속적으로 유지하는 것이 중요하다.
    
- **경계(Bounded Context) 정의의 어려움:**
    
    도메인을 명확하게 분리하는 것은 핵심적인 작업이지만, 현실에서는 각 컨텍스트 간의 경계 설정이 쉽지 않을 수 있다. 잘못 정의하면 시스템 간의 결합도가 높아질 위험이 있다.
    
- **비용 및 시간 투자:**
    
    초기 도메인 모델링과 전략적 설계 단계에 많은 시간과 노력이 필요하며, 이는 프로젝트 초기 비용 증가로 이어질 수 있다. 프로젝트의 규모와 복잡성에 따라 적절한 투자 여부를 판단해야 한다.
    
- **기존 시스템과의 통합:**
    
    기존 시스템이나 레거시 코드와 통합할 때, DDD의 개념을 적용하기 어려울 수 있으며, 적절한 안티-코럽션 레이어 등 통합 전략을 마련해야 한다.
    
    *안티-코럽션 레이어: 
    
    안티-코럽션 레이어(ACL)는 외부 시스템이나 레거시 시스템과 내부 도메인 모델 사이의 **"번역기"** 역할을 하는 설계 패턴이다. 이를 통해 서로 다른 모델 간의 직접적인 의존성을 피하고, 내부 도메인 모델이 외부 시스템의 변화에 영향을 받지 않도록 보호할 수 있다.
    
- **일관성 유지:**
    
    전술적 설계(엔티티, 애그리거트, 도메인 서비스 등)와 전략적 설계(컨텍스트, 경계 등)가 서로 잘 맞물려야 시스템 전반의 일관성이 유지된다. 그렇지 않으면 모델이 산만해질 위험이 있다.
    

## 추가 사항

### 도메인 이벤트 Domain Event

**개념 및 역할**

- **정의:**
    
    도메인 이벤트는 시스템 내에서 비즈니스 규칙이나 프로세스에 따라 중요한 상태 변화가 발생했음을 나타내는 이벤트이다. 예를 들어, 주문이 생성되거나 결제가 완료되면 해당 이벤트를 시스템 내에서 발행한다.
    
- **느슨한 결합:**
    
    도메인 이벤트를 사용하면 이벤트를 발생시키는 컴포넌트와 이를 처리하는 컴포넌트 사이의 직접적인 의존성을 줄인다. 이벤트를 수신하는 쪽은 이벤트의 발생 사실만 인지하면 되므로, 두 컴포넌트가 독립적으로 진화할 수 있다.
    
- **비동기 처리 및 확장성:**
    
    이벤트 기반 아키텍처에서는 이벤트를 큐에 쌓아 비동기로 처리할 수 있다. 이를 통해 시스템이 높은 부하를 처리할 때 유연하게 대응할 수 있으며, 여러 컴포넌트가 이벤트를 독립적으로 처리한다.
    

**예시**

- **온라인 쇼핑몰:**
    
    고객이 주문을 완료하면 `OrderPlaced` 이벤트가 발생한다. 이 이벤트를 수신한 후에,
    
    - **재고 관리 시스템은** 주문한 상품의 재고를 감소시키거나 업데이트한다.
    - **알림 시스템은** 고객에게 주문 확인 메시지를 보낸다.
    - **배송 시스템은** 배송 준비 프로세스를 시작한다.
    
    이렇게 각 시스템이 독립적으로 이벤트에 반응함으로써, 주문 처리 과정이 모듈화되고 유지보수가 용이해진다.
    

**핵심 포인트**

- 도메인 이벤트는 시스템의 상태 전환을 명시적으로 표현한다.
- 발행자와 구독자 간의 느슨한 결합을 유지하여 시스템 확장 및 변경에 유리하다.
- 이벤트 기반 통신을 통해 비동기 처리가 가능해지며, 시스템의 반응성과 확장성이 향상된다.

### 애그리게이션 및 일관성 보장

**애그리거트의 개념**

- **애그리거트 (Aggregate):**
    
    도메인 내의 관련 객체들을 하나의 단위로 묶어 하나의 트랜잭션 단위로 관리할 수 있도록 한 모델이다. 애그리거트는 일관된 상태를 유지하며, 외부에서는 오직 **애그리거트 루트 (Aggregate Root)**를 통해서만 내부 객체에 접근한다.
    
- **애그리거트 루트:**
    
    애그리거트 내의 중심 객체로, 해당 애그리거트에 속한 모든 객체의 일관성 및 규칙을 관리한다. 예를 들어, 주문(애그리거트 루트)에는 주문 항목, 결제 정보 등이 포함되며, 외부에서는 주문 루트를 통해서만 이 정보에 접근한다.
    

**일관성 보장**

- **트랜잭션 경계 설정:**
    
    애그리거트는 트랜잭션의 경계로 작용한다. 한 애그리거트 내에서 여러 객체에 대한 변경이 발생할 때, 이를 하나의 트랜잭션으로 묶어 데이터의 일관성을 보장한다. 이를 통해 도메인 규칙이 깨지지 않고 모든 변경이 원자적으로 적용된다.
    
- **불변성 및 비즈니스 규칙 적용:**
    
    애그리거트는 내부 상태의 불변성을 유지하도록 설계된다. 애그리거트 루트는 애그리거트 전체에 대해 비즈니스 규칙을 강제하며, 변경이 외부에서 직접 이루어지지 않도록 한다.
    
- **경계 분리:**
    
    애그리거트 간에는 직접적인 데이터 변경이 발생하지 않도록 경계를 명확하게 구분한다. 각 애그리거트는 독립적인 일관성을 유지하며, 다른 애그리거트와의 관계는 도메인 이벤트나 도메인 서비스를 통해 간접적으로 조율된다.
    

**예시**

- **은행 계좌 애그리거트:**
은행 계좌(애그리거트 루트)는 입금, 출금 등의 행위를 수행하며 계좌 잔액을 관리한다.
    - 한 트랜잭션 내에서 여러 입출금이 동시에 발생할 때, 애그리거트는 계좌의 최종 잔액이 일관되게 유지되도록 보장한다.
    - 계좌 간 자금 이체는 각 계좌의 애그리거트가 독립적으로 관리되며, 이체 관련 복잡한 규칙은 도메인 이벤트나 도메인 서비스를 통해 조율된다.

**핵심 포인트**

- **애그리거트**는 도메인 모델의 일관성을 유지하기 위한 단위로, 내부 객체들이 하나의 트랜잭션 단위로 관리된다.
- 외부에서는 **애그리거트 루트**를 통해 애그리거트 내부 객체에 접근하여 데이터 변경을 통제하고 비즈니스 규칙을 적용한다.
- 이 구조는 복잡한 비즈니스 로직과 데이터 무결성을 관리하는 데 필수적이다.

public class Customer {

### 3. 인프라스트럭처 계층

### 저장소 구현체 (CustomerRepositoryImpl.java)

```java
java
복사
package com.example.myapp.infrastructure.repository;

import com.example.myapp.domain.model.Customer;
import com.example.myapp.domain.repository.CustomerRepository;
import org.springframework.stereotype.Repository;

import java.util.HashMap;
import java.util.Map;
import java.util.Optional;

@Repository
public class CustomerRepositoryImpl implements CustomerRepository {

    // 간단한 예시를 위한 메모리 기반 저장소
    private Map<Long, Customer> database = new HashMap<>();
    private Long idSequence = 1L;

    @Override
    public Optional<Customer> findById(Long id) {
        return Optional.ofNullable(database.get(id));
    }

    @Override
    public void save(Customer customer) {
        // ID가 없으면 새로 할당
        if (customer.getId() == null) {
            customer.setId(idSequence++);
        }
        database.put(customer.getId(), customer);
    }
}

```

## 설명

- **도메인 계층:**
    
    비즈니스의 핵심 개념과 규칙(예: `Customer` 엔티티)을 정의한다. 저장소 인터페이스(`CustomerRepository`)도 여기에 포함되어 도메인 모델과 관련된 데이터 접근 계약을 정의한다.
    
- **애플리케이션 계층:**
    
    도메인 모델을 활용하여 사용 사례(비즈니스 로직)를 조합한다. 예를 들어, `CustomerService`는 고객 등록 로직을 수행하며 도메인 계층의 엔티티와 저장소 인터페이스를 호출한다.
    
- **인프라스트럭처 계층:**
    
    데이터베이스와 같은 외부 시스템과의 구체적 연동을 담당한다. 여기서는 메모리 기반의 간단한 구현(`CustomerRepositoryImpl`)을 예시로 들었지만, 실제 환경에서는 JPA나 MyBatis 등으로 대체할 수 있다.
    
- **인터페이스 계층:**
    
    외부에 API나 사용자 인터페이스를 제공하는 부분이다. `CustomerController`는 HTTP 요청을 받아 애플리케이션 계층의 서비스로 전달한다.
    
- **도메인 계층 (domain):**
    
    핵심 비즈니스 로직, 도메인 모델, 엔티티, 밸류 오브젝트, 도메인 이벤트 등을 포함한다. 이 계층은 비즈니스 규칙을 집중적으로 관리하며, 다른 계층에 의존하지 않아야 한다.
    
- **애플리케이션 계층 (application):**
    
    도메인 계층을 활용하여 구체적인 비즈니스 사용 사례를 구현한다. 서비스, 명령 핸들러 등이 이 계층에 위치하며, 도메인 로직을 조합해 클라이언트의 요구사항을 처리한다.
    
- **인프라스트럭처 계층 (infrastructure):**
    
    데이터베이스, 메시징 시스템, 외부 API 등 실제 시스템과의 통신 및 기술적 세부 구현을 담당한다. 도메인 계층은 이 계층에 의존하지 않고, 인터페이스(추상화)를 통해서만 상호작용하게 된다.
    
- **인터페이스 계층 (interfaces):**
    
    외부에 제공하는 API나 UI, 그리고 클라이언트와의 통신을 담당한다. REST API, 웹소켓, UI 컨트롤러 등이 포함된다.
    

이와 같이 폴더명을 나누는 이유:

1. **관심사의 분리 (Separation of Concerns):**
    
    각 계층이 자신의 책임에만 집중하도록 하여 코드의 복잡도를 낮추고, 유지보수성을 높인다.
    
2. **응집력 강화 (Cohesion):**
    
    동일한 목적과 역할을 가진 클래스들을 한 곳에 모아둠으로써, 관련 코드들이 자연스럽게 함께 유지되고 이해하기 쉬워진다.
    
3. **의존성 관리 (Dependency Management):**
    
    핵심 비즈니스 로직(도메인 계층)이 외부 인프라스트럭처나 인터페이스의 변화에 영향을 받지 않도록 격리하여, 변경에 유연하게 대응할 수 있다.
    
4. **확장성과 테스트 용이성:**
    
    각 계층이 분리되어 있기 때문에 새로운 기능 추가나 테스트 작성 시 독립적으로 작업할 수 있으며, 모듈 간 결합도를 낮춰 확장하기 좋다.

## Docker State

**개념 및 역할**  
Docker 컨테이너의 상태는 해당 컨테이너가 현재 어떤 실행 상태에 있는지를 나타내며, 애플리케이션의 라이프사이클 관리 및 문제 해결에 중요한 역할을 합니다.

**주요 상태**

- **created**  
  컨테이너가 생성되었지만 아직 실행되지 않은 상태입니다.
  
- **running**  
  컨테이너가 정상적으로 실행되고 있는 상태입니다.
  
- **paused**  
  `docker pause` 명령어로 컨테이너의 모든 프로세스를 일시 중지한 상태입니다.
  
- **exited**  
  컨테이너 내의 프로세스가 종료되었으나, 컨테이너 자체는 삭제되지 않은 상태입니다.
  
- **restarting**  
  자동 재시작 정책(`--restart`)에 따라 컨테이너가 재시작 중인 상태입니다.
  
- **dead**  
  심각한 문제로 인해 Docker 데몬에서 컨테이너를 더 이상 제어할 수 없는 상태입니다.

**핵심 포인트**

- `docker ps -a` 명령어로 모든 컨테이너와 해당 상태를 확인할 수 있습니다.
- 상태 전이는 애플리케이션의 실행 및 장애 상황을 파악하는 데 중요한 정보를 제공합니다.
- 자동 재시작 정책(`--restart`)을 설정하면, 컨테이너가 예기치 않게 종료되었을 때 자동으로 복구할 수 있어 서비스 안정성이 향상됩니다.
- 컨테이너 상태를 모니터링하고 로그를 분석함으로써, 문제 발생 시 빠른 대응이 가능해집니다.

**추가 고려 사항**

- **로그와 모니터링:**  
  Docker 컨테이너의 상태뿐만 아니라 로그 파일(예: `docker logs <컨테이너명>`)을 주기적으로 모니터링하여, 애플리케이션의 이상 징후를 조기에 발견할 수 있습니다.
  
- **상태 관리 도구:**  
  Prometheus, Grafana 등 모니터링 도구를 사용하면 컨테이너의 상태와 자원 사용량을 실시간으로 확인할 수 있어 운영자가 시스템 전체의 건강 상태를 파악하는 데 도움을 줍니다.

## Docker Volume

**개념 및 역할**  
Docker Volume은 컨테이너의 데이터를 호스트 시스템과 분리하여 영속적으로 저장할 수 있도록 하는 메커니즘입니다.  
컨테이너가 삭제되거나 재시작되더라도 볼륨에 저장된 데이터는 유지되므로, 데이터 무손실이 중요한 애플리케이션(예: 데이터베이스, 로그 저장 등)에서 필수적으로 사용됩니다.

**볼륨 종류**

1. **Anonymous Volume (익명 볼륨)**  
   - `docker run -v /app/data`와 같이 컨테이너 경로만 지정하면, Docker가 임의의 이름으로 익명 볼륨을 생성합니다.
   - 이름이 지정되지 않으므로 관리 및 추적이 어려울 수 있으며, 컨테이너 삭제 후에도 남아 있을 수 있어 주기적인 정리가 필요합니다.

2. **Named Volume (이름 있는 볼륨)**  
   - `docker volume create my-volume` 또는 `docker run -v my-volume:/app/data`와 같이 명시적으로 이름을 지정하는 방식입니다.
   - `docker volume ls` 명령어로 목록 확인이 가능하며, 재사용 및 관리가 용이합니다.
   - 이름 있는 볼륨은 여러 컨테이너 간에 데이터를 공유할 때도 유용합니다.

3. **Bind Mount (바인드 마운트)**  
   - `docker run -v /host/path:/app/data`처럼 호스트의 특정 디렉토리를 컨테이너의 경로에 직접 연결하는 방식입니다.
   - 개발 환경에서는 코드 변경 사항을 실시간 반영하거나 로컬 파일 시스템을 그대로 사용하기에 편리합니다.
   - 운영 환경에서는 호스트의 권한, 보안, 파일 시스템 구조에 직접 의존하므로 신중하게 사용해야 합니다.

**사용 예시**

```bash
# 1. 이름 있는 볼륨 생성
docker volume create my-volume

# 2. 이름 있는 볼륨을 사용하여 MySQL 컨테이너 실행
docker run -d \
  --name my-mysql-container \
  -v my-volume:/var/lib/mysql \
  mysql:8.0

## 배경

최근 모빌리티 서비스 발전과 함께 자율주행 기술과 스마트 주차 시스템에 대한 관심이 증대되고 있다. 도시 내 차량 증가와 주차 공간 부족 문제는 갈 수록 심해지고 있으며, 기존 네이티브 앱 기반 주차 및 호출 서비스는 하차 후 경험 개선에 한계가 있음이 지적되고 있다. 테슬라의 Smart Summon 등이 서비스 되고 있으나, 제한된 환경과 기능적 제약으로 인해 보다 통합적이고 혁신적인 서비스 구현의 필요성이 대두되고 있다.

## 목적

본 프로젝트의 목적은 자율주행 기반의 자동 주차 및 복귀 시스템을 구현하여 차량 사용자의 편의성을 극대화하는 데 있다. 구체적으로, 사용자가 하차한 후 차량이 스스로 최적의 주차 공간을 탐색·주차하고, 필요 시 원격 호출을 통해 자동으로 현재 위치로 복귀하는 기능을 제공함으로써 기존 주차 시스템의 한계를 극복하고자 한다. 또한, 주차장 도착 시 자동 결제 및 데이터 연동 기능을 통해 통합적인 모빌리티 서비스를 실현하며, 실제 경로 데이터와 시뮬레이션 환경을 연계하여 시스템의 현실성과 신뢰성을 확보하는 것을 목표로 한다.

### 차량 호출 시나리오

### 목표

사용자가 원하는 위치에서 차량을 원격으로 호출하여 차량이 자동으로 사용자의 위치로 이동하도록 한다.

### 참여자

- **주 사용자**: 차량 소유자 (운전자)
- **시스템**: 원격 호출 시스템, 자율 주행 시스템, 서버 (현재 위치확인 및 경로 설정)

### 사전 조건

- 차량이 주차되어 있고, 원격 호출 기능이 활성화되어 있어야 한다.
- 사용자의 스마트폰에 Vanish 앱이 설치되어 있고, 로그인 상태여야 한다.
- 차량과 Vanish 앱이 네트워크로 연결되어 있어야 한다.

### 기본 흐름

1. 사용자가 Vanish 앱을 실행하여 "차량 호출" 기능을 선택한다.
2. 현재 위치가 지도 상에 자동으로 표시되며, 사용자는 차량 호출을 요청한다.
3. 시스템은 차량의 현재 위치와 사용자의 위치를 비교하여 최적 경로를 설정한다.
4. 차량은 자율 주행을 통해 사용자의 위치로 이동한다.
5. 차량이 도착하면 앱에 "차량 도착" 알림이 전송된다.
6. 사용자는 차량에 탑승하여 주행을 시작한다.

### 예외 흐름

- **경로 장애물 발생**: 이동 중 장애물이 발생할 경우, 차량은 경로를 재설정하고 사용자는 앱을 통해 경로 재설정 사실을 안내받는다.
- **네트워크 오류**: 호출 중 네트워크 문제가 발생하면, 사용자는 "호출 실패, 다시 시도해 주세요"라는 메시지를 받는다.
- **주차장 출입 제한**: 차량이 주차장에서 출입이 불가능한 경우, 사용자는 "출입 불가, 수동 조작 필요"라는 메시지를 받는다.

### 결과

- 차량은 사용자의 호출에 따라 정확하게 현재 위치로 도착한다.
- 사용자는 편리하게 차량을 호출하고 이동할 수 있다.

# Docker 레이어의 기본 개념

## 불변성
- Dockerfile의 각 명령어 (FROM, RUN, COPY 등)는 새로운 레이어를 생성하며, 각 레이어는 변경 불가능합니다.

## 캐시 활용
- 도커는 이전 빌드의 레이어를 캐시하여, 동일한 명령어가 반복될 때 재빌드를 방지합니다.
- 이를 위해 자주 변경되지 않는 명령어는 상단에 배치하는 것이 좋습니다.

# 최적화 방법

## 명령어 결합
- 여러 RUN 명령어를 하나의 RUN 명령어로 합치면 중간 레이어를 줄일 수 있습니다.

```Dockerfile
RUN apt-get update && apt-get install -y package1 package2 && \
    rm -rf /var/lib/apt/lists/*
```
## 불필요한 파일 제거
- 빌드 과정에서 생성되는 임시 파일이나 캐시 파일은 즉시 삭제하여 최종 이미지 크기를 줄입니다.

## 멀티 스테이지 빌드
- 빌드 단계와 최종 실행 환경을 분리하여, 빌드에 필요한 파일만 최종 이미지에 포함시키는 방법입니다.

```Dockerfile
FROM builder AS build
RUN make build

FROM alpine
COPY --from=build /app /app
CMD ["/app/start"]
```

## .dockerignore 활용
- 빌드 컨텍스트에 포함될 불필요한 파일을 제외시켜, 이미지 빌드 과정의 효율을 높입니다.

# Vanish (Advanced Auto Valet Parking System) 요구사항 명세서

# 1. 시스템 개요

## 1.1 목적

본 문서는 향상된 AVP 서비스인 Vanish의 요구사항명세를 목적으로 한다. Vanish는 자율주행을 활용하여 승하차의 불편함을 최소화하고, 차량이 스스로 주변 주차장을 탐색하여 주차한 후, 사용자의 호출 시 자동으로 현재 위치로 복귀하는 시스템을 구현함으로써 기존 차량 서비스의 부가 가치를 극대화하는 것을 목표로 한다.

## 1.2 범위

- 차량 자율 주행 시스템
- 차량 원격 호출 시스템
- 차량 자동 주차 시스템
- 차량 배회 시스템
- 주차장 자동 결제 시스템

# Docker 컨테이너 최적화

Docker 컨테이너 최적화는 이미지 크기 최소화, 빌드 효율 개선, 보안 강화, 그리고 런타임 성능 향상을 목표로 합니다.

---

## 1. 경량 이미지 사용
- **베이스 이미지 선택:**  
  - Alpine Linux 등 경량 베이스 이미지를 사용하면 불필요한 라이브러리 및 파일을 줄일 수 있습니다.
- **불필요한 패키지 제거:**  
  - 사용하지 않는 패키지나 파일을 설치하지 않거나, 설치 후 제거합니다.

---

## 2. Multi-Stage 빌드 활용
- **최종 산출물만 포함:**  
  - 여러 단계의 빌드를 사용해 빌드 도구와 불필요한 파일은 제외하고 최종 실행 파일만 포함시킵니다.
- **이미지 크기 감소:**  
  - 최종 이미지에 필요한 파일만 남겨서 이미지 크기를 크게 줄일 수 있습니다.

---

## 3. 이미지 레이어 최적화
- **명령어 순서 최적화:**  
  - Dockerfile 작성 시 자주 변경되지 않는 명령어는 상단에, 자주 변경되는 부분은 하단에 배치하여 캐시 활용을 극대화합니다.
- **레이어 최소화:**  
  - 여러 명령어를 한 RUN 명령어로 묶어 불필요한 레이어 생성을 방지합니다.

---

## 4. 불필요한 파일 제거 및 .dockerignore 활용
- **임시 파일 및 캐시 삭제:**  
  - 빌드 후 남는 임시 파일, 로그, 캐시 등을 삭제합니다.
- **.dockerignore 파일:**  
  - 빌드 컨텍스트에 포함되지 않아도 되는 파일 및 디렉터리를 명시하여 이미지 크기를 줄입니다.

---

## 5. 환경 변수 및 설정 관리
- **외부 설정 활용:**  
  - Dockerfile 내에 하드코딩하지 않고, 환경 변수나 외부 설정 파일로 관리해 유연성을 높입니다.
- **Build-time arguments:**  
  - 빌드 시 필요한 인자를 전달하여 이미지 빌드 프로세스를 최적화합니다.

---

## 6. 보안 강화
- **최소 권한 원칙:**  
  - 컨테이너 내에서 root 사용자 대신 비권한 사용자로 실행하여 보안을 강화합니다.
- **취약점 스캐닝:**  
  - 이미지 취약점 스캐닝 도구를 활용해 보안 취약점을 사전에 파악하고 대응합니다.

---

## 7. 로그 및 모니터링 최적화
- **로깅 드라이버 설정:**  
  - 컨테이너 로그 관리 정책을 최적화하여 로그의 과도한 저장을 방지합니다.
- **모니터링 도구:**  
  - Prometheus, Grafana, ELK 스택 등 모니터링 도구를 사용해 컨테이너 상태를 지속적으로 확인합니다.

---

## 8. 리소스 제한 설정
- **리소스 할당:**  
  - `--memory`, `--cpu` 옵션을 활용해 각 컨테이너의 메모리 및 CPU 사용량을 제한하여, 시스템 전체의 안정성을 유지합니다.

## PG사란?

- PG(Payment Gateway)란 온라인에서 고객이 카드로 결제하면 카드사와 가맹점 간 통신을 연결해주는 서비스.

## 포트원

- 결제를 구현하기 위해서는 각 PG사에서 제공하는 API를 사용하여 개발을 진행해야 함. 이를 조금 더 쉽게 해결하고자 포트원이라는 업체 등장.
- 포트원은 PG 계약부터 기술지원 및 서비스 운영까지 전 단계에 걸쳐 결제서비스 이용에 도움을 주는 호스팅사.

## 1. 기본 결제 시스템 개요

**기본 결제 시스템**은 사용자가 주문할 때마다 결제를 직접 진행하는 시스템입니다.

주요 흐름은 다음과 같습니다.

1. **프론트엔드 요청:**
    - 사용자가 결제 버튼을 클릭하면 결제 모듈(포트원에서 제공하는 JavaScript 라이브러리 등)을 호출합니다.
    - 결제 정보(주문번호, 결제 금액, 구매자 정보 등)를 포함한 결제 요청이 포트원 API로 전송됩니다.
2. **결제 승인 및 콜백:**
    - 포트원에서 결제 승인 여부를 결정하고, 결제 완료 후 프론트엔드에 결과(승인/거절)를 반환합니다.
    - 동시에 백엔드로 결제 결과에 대한 콜백(혹은 별도의 검증 API 호출)을 보내어 결제 정보를 검증합니다.
3. **백엔드 검증 및 저장:**
    - 백엔드(Spring Boot)를 통해 포트원으로부터 전달받은 결제 정보(예: imp_uid 혹은 포트원에서 제공하는 고유 결제 ID)를 이용해 결제 상태, 결제 금액 등을 검증합니다.
    - 검증이 완료되면 주문 처리, DB에 결제 내역 저장, 후속 처리(예: 이메일 전송 등)를 진행합니다.

---

## 2. 포트원(PortOne) 활용

포트원은 결제 API를 제공하는 PG(결제 대행사) 서비스로,

다음과 같은 기능을 제공합니다.

- **결제 요청 및 승인:** 다양한 결제 수단(카드, 계좌이체 등)을 지원하며, 실시간 결제 승인을 처리합니다.
- **보안 기능:** 결제 데이터 암호화 및 토큰화를 통한 보안 강화
- **결제 결과 콜백:** 결제 완료 후, 결제 상태와 관련된 정보를 제공하여 백엔드 검증을 용이하게 함

포트원의 개발자 문서를 참고하여 API 키, 결제 모듈 초기화, 요청 파라미터 등에 대해 정확히 설정해야 합니다.

### A. 프론트엔드

포트원에서 제공하는 JavaScript 라이브러리를 이용해 결제 요청을 보내는 방식은 iamport와 유사합니다.

아래는 기본적인 예시 코드입니다.

```html
html
복사
<!DOCTYPE html>
<html lang="ko">
<head>
  <meta charset="UTF-8">
  <title>포트원 결제 테스트</title>
  <!-- 포트원 결제 라이브러리 (실제 제공되는 URL 사용) -->
  <script type="text/javascript" src="https://cdn.portone.com/js/portone.payment.js"></script>
  <script type="text/javascript">
    // 포트원 결제 라이브러리 초기화 (가맹점 식별코드 사용)
    var PORTONE = window.PORTONE;
    PORTONE.init("내_포트원_식별코드");

    function requestPayment() {
      PORTONE.requestPay({
        pg: "{PG사 코드}.{상점ID}",      // 실제 포트원 가맹점 정보를 입력
        pay_method: "card",             // 결제 수단
        merchant_uid: "ORD" + new Date().getTime(),  // 고유 주문번호 생성
        name: "상품명 예시",
        amount: 10000,                  // 결제 금액
        buyer_email: "user@example.com",
        buyer_name: "홍길동",
        buyer_tel: "010-1234-5678",
        buyer_addr: "서울시 강남구",
        buyer_postcode: "12345"
      }, function (rsp) {              // 결제 결과 콜백 함수
        if (rsp.success) {
          // 결제 성공 시 백엔드로 검증 요청
          fetch('/verify/' + rsp.payment_id, {  // rsp.payment_id: 포트원에서 반환하는 결제 고유값
            method: 'POST',
            headers: { 'Content-Type': 'application/json' },

          })
          .then(response => response.json())
          .then(data => {
            if(data.verified){
              alert("결제 성공");
            } else {
              alert("결제 검증 실패");
            }
          });
        } else {
          alert("결제 실패: " + rsp.error_msg);
        }
      });
    }
  </script>
</head>
<body>

### B. 백엔드(Spring Boot)

Spring Boot 애플리케이션에서는 결제 결과를 검증하는 REST API 엔드포인트를 구현합니다.

예를 들어, 포트원 API로부터 결제 내역을 조회하여 결제 금액, 상태 등을 확인하는 로직이 필요합니다.

**예시: PaymentController.java**

```java
java
복사
@RestController
@RequestMapping("/verify")
public class PaymentController {

    @Autowired
    private PaymentService paymentService; // 결제 검증 및 저장 로직을 담당하는 서비스

    @PostMapping("/{paymentId}")
    public ResponseEntity<Map<String, Object>> verifyPayment(
            @PathVariable String paymentId,
            @RequestBody Map<String, Object> requestBody) {

        // requestBody에 포함된 주문번호 등의 정보 추출
        String merchantUid = (String) requestBody.get("orderId");

        // 포트원 API를 호출하여 결제 정보를 조회(이를 위한 서비스 로직 구현 필요)
        PaymentInfo paymentInfo = paymentService.verifyPaymentWithPortOne(paymentId);

        // 결제 금액 및 주문번호 검증 (DB 조회 등 추가 검증 로직 포함)
        boolean isVerified = paymentService.comparePayment(paymentInfo, merchantUid);

        Map<String, Object> response = new HashMap<>();
        response.put("verified", isVerified);
        return ResponseEntity.ok(response);
    }
}
```

**서비스 계층에서는**

- 포트원 API와 통신할 때 RestTemplate 또는 WebClient를 이용해 결제 상세 정보를 요청합니다.
- 결제 내역이 DB에 저장된 주문 정보와 일치하는지 확인하고, 결제 성공 여부를 판단합니다.
- 검증이 완료되면, 주문 처리(예: 상품 배송 준비 등)나 추가 후속 작업을 진행합니다.

## 4. 구현 시 고려 사항

- **보안:**
    - 결제 관련 정보는 HTTPS 등 보안 통신을 통해 전송해야 합니다.
    - 민감한 데이터(예: 카드 정보)는 직접 저장하지 않고, 포트원에서 제공하는 토큰화 기능을 사용합니다.
    - 서버에서 포트원 API 호출 시 인증키, 시크릿 키 등은 안전하게 관리합니다.
- **주문번호 관리:**
    - merchant_uid는 고유값이어야 하므로, 중복되지 않도록 생성하는 로직(타임스탬프, UUID 등)을 적용합니다.
- **에러 처리 및 로깅:**
    - 결제 실패, 검증 실패 시 적절한 에러 메시지와 로깅을 통해 문제를 추적할 수 있도록 합니다.
    - 포트원 API 호출 시 네트워크 문제나 API 장애에 대비한 예외 처리를 구현합니다.
- **테스트 환경 구성:**
    - 포트원에서 제공하는 테스트 환경(샌드박스)을 활용하여 실제 결제가 이루어지기 전 다양한 시나리오를 테스트합니다.

## 1. 자동 결제 시스템 개요

1. **초기 동의 및 카드 정보 토큰화 (빌링 키 발급):**
    - 프론트엔드에서 고객이 자동 결제에 동의하면서 결제 정보를 입력합니다.
    - 결제 게이트웨이(포트원)를 통해 카드 정보를 토큰화하여 빌링 키(또는 저장 토큰)를 발급받습니다.
    - 이 빌링 키는 백엔드 DB에 저장되어 향후 자동 결제 시 사용됩니다.
2. **정기 결제 요청 (스케줄링):**
    - 백엔드에서 스케줄러(Spring Boot의 @Scheduled, Quartz, 또는 외부 스케줄링 시스템 등)를 통해 정해진 주기(예: 매월 1일, 매주 등)에 자동으로 결제 요청을 실행합니다.
    - 저장된 빌링 키와 결제 금액 등의 정보를 기반으로 포트원 API를 호출하여 자동 결제를 진행합니다.
3. **결제 결과 검증 및 후속 처리:**
    - 결제 게이트웨이에서 반환된 결제 결과를 확인한 후, 주문 상태 업데이트, 결제 기록 저장, 실패 시 재시도 또는 고객 알림 등의 처리를 수행합니다.

## 2. 프론트엔드 구성 예시

아래는 고객이 자동 결제에 동의하고, 빌링 키를 발급받아 백엔드에 저장하는 예시 코드입니다.

```html
html
복사
<!DOCTYPE html>
<html lang="ko">
<head>
  <meta charset="UTF-8">
  <title>자동 결제 설정</title>
  <!-- 포트원 결제 라이브러리 (실제 제공 URL 확인) -->
  <script type="text/javascript" src="https://cdn.portone.com/js/portone.payment.js"></script>
  <script type="text/javascript">
    // 포트원 결제 모듈 초기화 (실제 가맹점 식별코드 사용)
    var PORTONE = window.PORTONE;
    PORTONE.init("내_포트원_식별코드");

    function requestBillingKey() {
      PORTONE.requestBilling({
        pg: "{PG사 코드}.{상점ID}",    // 실제 값으로 변경
        pay_method: "card",
        merchant_uid: "AUTO" + new Date().getTime(),  // 고유 주문번호 생성
        name: "자동 결제 등록",
        amount: 10000,               // 최초 결제 금액 (예: 보증금 또는 첫 결제 금액)
        buyer_email: "user@example.com",
        buyer_name: "홍길동",
        buyer_tel: "010-1234-5678",
        buyer_addr: "서울시 강남구",
        buyer_postcode: "12345"
      }, function (rsp) {
        if (rsp.success) {
          // rsp.billing_key: 포트원에서 발급한 빌링 키
          // 백엔드에 빌링 키와 고객 정보를 저장하여 이후 자동 결제에 사용
          fetch('/billing/register', {
            method: 'POST',
            headers: { 'Content-Type': 'application/json' },
            body: JSON.stringify({
              billingKey: rsp.billing_key,
              merchantUid: rsp.merchant_uid,
              amount: 10000,
              buyerEmail: "user@example.com"
            })
          })
          .then(response => response.json())
          .then(data => {
            if(data.registered){
              alert("자동 결제 등록 성공");
            } else {
              alert("자동 결제 등록 실패");
            }
          });
        } else {
          alert("빌링 키 발급 실패: " + rsp.error_msg);
        }
      });
    }
  </script>
</head>
<body>
  <button onclick="requestBillingKey()">자동 결제 등록</button>
</body>
</html>

```

> 설명:
> 
> - 사용자가 결제 정보를 입력하면 포트원 결제 모듈이 빌링 키를 발급합니다.
> - 발급된 빌링 키는 AJAX 요청을 통해 백엔드의 `/billing/register` 엔드포인트에 전달되어 저장됩니다.

@RestController
@RequestMapping("/billing")
public class BillingController {

    @Autowired
    private BillingService billingService;

    @PostMapping("/register")
    public ResponseEntity<Map<String, Object>> registerBilling(@RequestBody BillingRequest billingRequest) {

## 4. 구현 시 고려사항

- **보안 및 토큰 관리:**
    - 빌링 키와 같은 민감한 정보는 안전하게 저장하고, HTTPS를 통해 통신해야 합니다.
    - 포트원 API 호출 시 필요한 인증 키와 시크릿은 환경 변수나 별도의 안전한 설정 파일로 관리합니다.
- **에러 및 예외 처리:**
    - 자동 결제 실패 시 재시도 로직, 고객에게 알림 기능 등을 마련하여 문제 발생 시 신속하게 대응할 수 있도록 합니다.
    - 네트워크 오류나 포트원 API 장애에 대비한 예외 처리 로직을 추가합니다.
- **테스트:**
    - 포트원 테스트 환경(샌드박스)을 활용해 다양한 시나리오(성공, 실패, 부분 실패 등)를 충분히 검증합니다.
- **스케줄링 관리:**
    - 스케줄러의 실행 시간, 간격 등을 비즈니스 요구사항에 맞게 설정하고, 장애 발생 시 재시작 정책을 마련합니다.

# MSA에서 ERD 설계하기

MSA에서는 서비스 단위로 DB를 각각 생성해주는 편이 좋다. 각각의 서비스가 독립적으로 동작하기 위해서는 서비스 별로 DB를 따로 생성하고, DB간의 참조 관계는 Bounded Context를 활용하여 이어주는 편이 좋다.

Bounded Context란?

![image.png](attachment:2c7c9312-055b-4fce-8164-b509221216a1:image.png)

같은 용어라도 하위 도메인마다 의미가 다르고 같은 대상이라도 지칭하는 용어가 다를 수 있다. 한 개의 모델로 모든 하위 도메인을 표현하려는 시도는 올바른 방법이 아니며 표현할 수도 없다.

하위 도메인마다 사용하는 용어가 다르기 때문에 올바른 도메인 모델을 개발하려면 하위 도메인마다 모델을 만들어야 한다.

모델은 특정한 컨텍스트하에서 완전한 의미를 갖는데, 이렇게 구분되는 경계를 갖는 컨텍스트를 DDD에서 Bounded Context라고 한다.

### 서비스 분할 기준 및 도메인 경계 설정

- **서비스 분리 기준**
    - 비즈니스 도메인과 하위 도메인 별로 서비스가 구분되어야 합니다.
    - 도메인 주도 설계(DDD)에서 강조하는 Aggregates, Entities, Value Objects 등을 활용하여 각 서비스의 경계를 명확히 합니다.
    - 데이터 일관성과 변경 주기를 고려하여, 변경이 잦은 데이터와 그렇지 않은 데이터를 분리하는 것이 좋습니다.
- **도메인 경계 정의**
    - 각 도메인은 자체 모델과 용어 체계를 갖추며, 다른 도메인과의 의존성을 최소화합니다.
    - 서비스 간 통신은 Bounded Context를 기준으로 하며, 컨텍스트 간의 통합은 명확한 계약(API, 이벤트 등)을 통해 이뤄집니다.

---

### 각 서비스별 DB 설계 원칙

- **데이터 정규화 및 스키마 설계**
    - 각 서비스는 독립적인 DB를 운영하므로, 해당 서비스에 최적화된 스키마를 구성합니다.
    - 정규화 과정을 통해 데이터 중복을 최소화하고, 필요 시 비정규화를 고려하여 성능과 확장성을 확보합니다.
- **샤딩 및 복제 전략**
    - 데이터량이 증가할 경우, 샤딩을 통해 DB 부하를 분산하고, 복제 전략을 활용해 가용성과 장애 복구 능력을 강화합니다.
    - 서비스 특성에 따라 읽기 전용 복제본과 쓰기 전용 인스턴스를 분리하는 것도 고려할 수 있습니다.
- **데이터 마이그레이션 방안**
    - 서비스 업데이트나 스키마 변경 시, 무중단 마이그레이션을 위해 버전 관리 및 단계별 마이그레이션 전략을 마련합니다.
    - 롤백 플랜을 포함하여 데이터 손실이나 장애에 대비할 수 있도록 설계합니다.

---

### Bounded Context 구체화

- **용어와 모델의 분리**
    - 각 하위 도메인은 독립적인 Bounded Context 내에서 용어와 모델을 정의합니다.
    - 동일한 용어라도 컨텍스트에 따라 다른 의미를 갖는 경우, 컨텍스트 명칭을 명시적으로 구분합니다.
- **컨텍스트 간 연결 방법**
    - 컨텍스트 간 통신은 API, 메시지 브로커 또는 이벤트 버스를 활용하여 구현합니다.
    - 데이터 연관성을 유지하기 위해 컨텍스트 간에 필요한 데이터는 동기/비동기 방식으로 교환하며, 데이터 중복 저장 시 동기화 메커니즘을 마련합니다.
- **구체적 사례 및 모델**
    - 예를 들어, 주문 서비스와 결제 서비스가 각기 다른 Bounded Context에 속할 경우, 주문 서비스에서는 주문 내역만 관리하고 결제 내역은 결제 서비스에서 관리하도록 분리합니다.
    - 이때, 주문 완료 이벤트를 발행하여 결제 서비스가 이를 수신하는 형태로 통합할 수 있습니다.

---

### 서비스 간 통신 및 데이터 일관성 전략

- **API 호출 및 이벤트 기반 통신**
    - 서비스 간 동기식 통신은 RESTful API 또는 gRPC를 통해 구현하고, 비동기식 통신은 메시지 큐나 이벤트 버스를 활용합니다.
    - 이벤트 소싱, CQRS 등의 패턴을 통해 읽기/쓰기 분리 및 데이터 일관성 유지를 고려합니다.
- **분산 트랜잭션 관리**
    - 서비스 간 트랜잭션은 Saga 패턴을 적용하여, 각 단계별 로컬 트랜잭션과 보상 트랜잭션을 통해 일관성을 관리합니다.
    - 트랜잭션 경계가 명확하지 않은 경우, eventual consistency(최종 일관성) 모델을 도입할 수 있습니다.

---

### API 게이트웨이 및 인터페이스 설계

- **API 게이트웨이 구성**
    - 외부 클라이언트와 내부 서비스 간 인터페이스를 분리하기 위해 API 게이트웨이를 두어, 인증, 로드밸런싱, 라우팅 등을 중앙에서 관리합니다.
- **인터페이스 설계 원칙**
    - RESTful API나 gRPC 등 명확한 인터페이스 표준을 적용하고, 각 서비스의 역할과 책임에 맞게 엔드포인트를 설계합니다.
    - 보안 측면에서는 인증, 인가, 암호화 등 정책을 적용하여 외부 공격 및 데이터 유출을 방지합니다.

---

### 에러 처리 및 장애 대응 전략

- **오류 상황에 대한 처리 방안**
    - 각 서비스는 자체적인 오류 처리 로직을 갖추고, 발생 가능한 예외 상황에 대해 명확한 응답 코드를 정의합니다.
- **로깅 및 모니터링**
    - 중앙 집중식 로그 수집 시스템 및 모니터링 도구를 도입하여, 서비스 상태 및 오류 상황을 실시간으로 파악할 수 있도록 합니다.
- **장애 복구 전략**
    - Circuit Breaker 패턴, 리트라이 로직, 백업 및 복구 방안을 마련하여, 서비스 장애 시 신속한 복구가 가능하도록 설계합니다.

---

### 보안 및 접근 제어

- **데이터 접근 권한 관리**
    - 각 서비스별로 접근 제어 정책을 수립하고, 역할 기반 접근 제어(RBAC)를 적용하여 불필요한 데이터 접근을 제한합니다.
- **서비스 간 보안 통신**
    - TLS 등 암호화 프로토콜을 사용하여 서비스 간 데이터 통신의 보안을 강화합니다.
- **인증 및 인가**
    - OAuth, JWT 등 표준 인증 방식을 도입하여 사용자 및 서비스의 신뢰성을 확보하며, 보안 정책을 지속적으로 점검합니다.

# Docker Compose 개요

- Docker Compose는 **여러 개의 컨테이너로 구성된 애플리케이션을 정의하고 실행하기 위한 도구**이다.
- **YAML 파일**을 사용하여 컨테이너의 설정 및 관계를 관리한다.

---

## 사용 목적

- 다중 컨테이너 환경에서 **빠른 환경 구축**과 **쉬운 관리**를 위해 사용
- 로컬 개발, 테스트, 배포 환경을 동일하게 유지할 수 있도록 지원

---

## 구성 요소 및 주요 개념

### ① docker-compose.yml 파일

- Docker Compose의 핵심으로 컨테이너 설정을 정의한다.
- 서비스(services), 네트워크(networks), 볼륨(volumes) 등을 정의한다.

**예시**

```yaml
yaml
복사편집
version: '3.8'

services:
  web:
    build: .
    ports:
      - "5000:5000"
    volumes:
      - .:/code
    depends_on:
      - redis

  redis:
    image: redis:alpine

```

### ② 서비스(services)

- 컨테이너로 실행할 개별 애플리케이션 단위
- 이미지, 포트, 볼륨, 환경변수 등을 정의할 수 있다.

### ③ 네트워크(networks)

- 서비스 간 네트워크를 정의하여 통신할 수 있게 설정
- 명시하지 않으면 기본(default) 네트워크 사용

### ④ 볼륨(volumes)

- 데이터를 컨테이너 외부에 영구적으로 저장하기 위해 사용

---

## 주요 명령어

- 구성된 서비스를 시작하고 중지하는 주요 명령어는 다음과 같다.

| 명령어 | 설명 |
| --- | --- |
| `docker compose up` | 컨테이너를 생성하고 실행 |
| `docker compose up -d` | 백그라운드에서 컨테이너 실행 |
| `docker compose down` | 컨테이너 및 관련 네트워크 중지 및 제거 |
| `docker compose build` | 서비스의 이미지 빌드 |
| `docker compose ps` | 실행 중인 컨테이너 상태 확인 |
| `docker compose logs` | 컨테이너 로그 확인 |

---

## Docker Compose 장점

- **환경 일관성 유지** 및 간편한 설정 공유
- 여러 컨테이너 관리가 쉽고 효율적
- 빠른 개발 및 테스트 환경 구축 가능

---

## 정리

Docker Compose는 여러 컨테이너 기반 애플리케이션 환경에서 설정과 실행을 편리하게 관리하는 필수적인 도구이다. YAML 파일을 통해 빠르고 간편하게 컨테이너 간 연결 및 설정을 정의할 수 있다.

# Docker 디버깅 개요

Docker 환경에서 문제가 발생했을 때, 원인을 찾고 해결하는 과정이다. 주로 컨테이너 실행, 이미지 빌드, 네트워크 문제, 볼륨 관리 등과 관련된 이슈가 발생한다.

---

## 주요 디버깅 이슈 유형

- **컨테이너 실행 오류**
- **컨테이너 상태 점검 (비정상 종료 등)**
- **이미지 빌드 실패**
- **포트 바인딩 및 네트워크 문제**
- **파일 및 볼륨 관련 문제**

---

## Docker 디버깅 방법

### ① 컨테이너 로그 확인

컨테이너가 정상적으로 실행되지 않을 때 가장 먼저 할 작업이다.

```
shell
복사편집
docker logs [컨테이너명 또는 ID]

```

- 실시간 로그 보기

```
shell
복사편집
docker logs -f [컨테이너명 또는 ID]

```

### ② 컨테이너 상태 확인

컨테이너가 실행 중인지, 혹은 종료 상태인지 확인한다.

```
shell
복사편집
docker ps -a

```

### ③ 컨테이너 내부 진입

실행 중인 컨테이너에 접속하여 내부 상태를 점검한다.

```
shell
복사편집
docker exec -it [컨테이너명 또는 ID] sh
# bash 쉘 접속
docker exec -it [컨테이너명 또는 ID] bash

```

### ④ 이미지 빌드 실패 시 디버깅

Dockerfile 빌드 중 실패할 경우 로그를 보고 원인을 파악한다.

```
shell
복사편집
docker build -t [이미지명] .

```

- 중간 단계부터 빌드하여 빠르게 오류를 찾는다. (캐시 활용)

```
shell
복사편집
docker build --no-cache -t [이미지명] .

```

### ⑤ 포트 및 네트워크 점검

포트 충돌 및 네트워크 연결 오류 시 확인

```
shell
복사편집
docker network ls
docker network inspect [네트워크명]

# 포트 확인
docker ps
netstat -anp | grep [포트번호]

```

### ⑥ 볼륨 디버깅

볼륨이 제대로 연결되지 않았거나 데이터를 찾을 수 없을 때

```
shell
복사편집
docker volume ls
docker volume inspect [볼륨명]

```

### ⑦ Docker 시스템 자원 상태 점검

Docker가 리소스 부족으로 비정상 작동할 경우를 점검한다.

```
shell
복사편집
docker stats

```

---

## 디버깅을 위한 유용한 팁

- 이미지를 빌드할 때 레이어를 최소화하면 디버깅이 쉬워진다.
- 컨테이너는 최소한의 프로세스만 실행하는 것이 디버깅에 유리하다.
- 명확한 컨테이너 명칭과 태그를 사용하면 디버깅이 편리하다.

---

## 정리

Docker 디버깅은 문제 유형에 따라 적절한 도구를 선택해 문제 원인을 신속히 찾아 해결하는 과정이다. 각종 Docker 명령어(logs, exec, inspect 등)를 적극 활용하여 빠르게 문제를 진단하고 해결할 수 있어야 한다.

## 1. Set up Docker’s apt repository

<aside>
💡

과정 요약

1. **시스템 준비:** 최신 패키지 목록을 업데이트하고, HTTPS 통신과 데이터 전송에 필요한 도구들을 설치합니다.
2. **GPG 키 설정:** Docker 저장소의 신뢰성을 확인하기 위해 GPG 키를 다운로드하고 올바른 권한으로 설정합니다.
    - Docker 저장소에서 제공하는 소프트웨어 패키지의 출처와 무결성을 보장하기 위해 사용되는 디지털 서명 키
3. **저장소 추가:** Docker 저장소 정보를 apt 소스에 추가하여, 이후 Docker Engine을 설치할 때 해당 저장소에서 패키지를 가져올 수 있도록 합니다.
4. **최종 업데이트:** 추가한 저장소의 패키지 목록을 포함하도록 시스템의 패키지 목록을 다시 업데이트합니다.

이 과정을 완료하면, `sudo apt-get install docker-ce docker-ce-cli containerd.io` 등의 명령어를 통해 Docker Engine을 설치할 수 있습니다.

</aside>

```bash
# Add Docker's official GPG key:
# GPG 키 설정 및 저장소 준비

# 시스템 패키지 목록 업데이트
sudo apt-get update

# 필수 패키지 설치 
# ca-certificates: SSL 인증서를 관리하여 HTTPS 연결 시 보안 검증을 가능하게 함.
# curl: URL을 통해 데이터를 전송받거나 다운로드할 때 사용하는 도구.
sudo apt-get install ca-certificates curl

# /etc/apt/keyrings 디렉토리 생성. 이 디렉토리는 Docker의 GPG 키를 저장할 위치.
# -m 0755: 디렉토리의 권한을 설정, -d: 디렉토리를 생성하는 옵션
sudo install -m 0755 -d /etc/apt/keyrings

# Docker의 공식 GPG 키 다운로드하여 /etc/apt/keyrings/docker.asc 파일에 저장.
# -f: HTTP 요청 실패 시 에러를 발생. -s: 진행 상황을 출력하지 않음. -S: 에러 발생 시 메시지 출력
# -L: 리다이랙션이 있을 경우 따라감. -o: 결과를 지정한 파일로 저장.
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc

# 다운로드한 GPG 키 파일에 대해 모든 사용자에게 읽기 권한을 부여
# apt가 Docker 저장소의 패키지를 검증할 때 필요
sudo chmod a+r /etc/apt/keyrings/docker.asc

# Add the repository to Apt sources:
# apt 소스 리스트에 Docker 저장소 추가
# deb: Debian 패키지 형식의 저장소임을 지정.
# [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.asc]:
# arch=$(dpkg --print-architecture): 현재 시스템의 아키텍처(예: amd64)를 자동으로 감지.
# signed-by=/etc/apt/keyrings/docker.asc: 이 저장소의 패키지가 지정된 GPG 키로 서명되었음을 지정.
# https://download.docker.com/linux/ubuntu: Docker의 공식 Ubuntu 저장소 URL.
# $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}"):
# /etc/os-release 파일에서 Ubuntu의 코드네임(예: focal, jammy 등)을 추출.
# stable: 안정 채널의 패키지를 사용하겠다는 의미.
# sudo tee 명령어를 사용해 /etc/apt/sources.list.d/docker.list 파일에 저장
# > /dev/null: 터미널 출력 내용 숨김.
echo \
  "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.asc] https://download.docker.com/linux/ubuntu \
  $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}") stable" | \
  sudo tee /etc/apt/sources.list.d/docker.list > /dev/null
sudo apt-get update
```

## Nginx 실행

```bash
docker run -d \
  --name nginx \
  -p 80:80 \
  --network vanish-net \
  -v ~/nginx/conf.d:/etc/nginx/conf.d \
  -v ~/nginx/html:/usr/share/nginx/html \
  nginx
```

### Nginx 설정 파일 작성 (HTTP → HTTPS 리디렉션 포함)

- **vim ~/nginx/conf.d/default.conf**

<aside>
💡

~/nginx/conf.d/default.conf 내용:

</aside>

```yaml
server {
    listen 80; # 80번 포트로 요청을 수신
    server_name j12a707.p.ssafy.io; # 이 설정이 적용될 도메인
		
		# 인증서 발급 시 필요한 파일 경로
    location /.well-known/acme-challenge/ {
        root /usr/share/nginx/html;
    }

    # 모든 요청을 HTTPS로 리디렉션
    location / {
        return 301 https://$host$request_uri;
    }
}
```

- Let’s Encrypt가 http://j12a707.ssafy.io/.well-known/acme-challenge/xxx 경로에 접근해서 검증 파일을 찾기 때문에, 이 부분은 HTTPS로 리디렉션되면 안됨.
- 그래서 이 경로만 예외적으로 /usr/share/nginx/html에서 직접 응답하게 설정.

### Cerbot 설치 (EC2 내부에서 진행)

```bash
sudo apt update
sudo apt install certbot
```

### HTTPS 인증서 발급

```bash
sudo certbot certonly \
  --webroot \
  -w ~/nginx/html \
  -d j12a707.p.ssafy.io
```

- 인증 성공시, 아래의 경로에 인증서가 생김.
- /etc/letsencrypt/live/j12a707.ssafy.io/
- 이 경로는 Docker에 cert 폴더로 마운트 되어 있어서 Nginx에서 바로 접근 가능

  --network vanish-net \
  -v ~/nginx/conf.d:/etc/nginx/conf.d \
  -v ~/nginx/html:/usr/share/nginx/html \
  -v ~/nginx/cert:/etc/letsencrypt \

### Nginx HTTPS 설정 추가

- vim ~/nginx/conf.d/default.conf

<aside>
💡

~/nginx/conf.d/default..conf 전체 수정 :

</aside>

server {
    listen 80;
    server_name j12a707.p.ssafy.io;

    location /.well-known/acme-challenge/ {
        root /usr/share/nginx/html;
    }

    location / {
        return 301 https://$host$request_uri;
    }
}

# 2. HTTPS 정적 파일 + API 프록시
server {
    listen 443 ssl;
    server_name j12a707.p.ssafy.io;

    ssl_certificate /etc/letsencrypt/live/j12a707.p.ssafy.io/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/j12a707.p.ssafy.io/privkey.pem;
		
		# 프론트: 정적 파일
    location / {
        root /usr/share/nginx/html;
        index index.html;
        try_files $uri /index.html;
    }
		
		# 백엔드: API Gateway로 프록시
    location /api/ {
        proxy_pass http://api-gateway:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        
    
}

```

- proxy_set_header Host $host;
    - 클라이언트가 요청할 때 사용한 도메인 이름을 백엔드 서버로 전달
- proxy_set_header X-Real-IP $remote_addr;
    - 사용자의 실제 IP 주소를 X-Real-IP 헤더에 담아서 백엔드로 전달
