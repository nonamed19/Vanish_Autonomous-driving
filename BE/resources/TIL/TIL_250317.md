
# MSA에서 ERD 설계하기

MSA에서는 서비스 단위로 DB를 각각 생성해주는 편이 좋다. 각각의 서비스가 독립적으로 동작하기 위해서는 서비스 별로 DB를 따로 생성하고, DB간의 참조 관계는 Bounded Context를 활용하여 이어주는 편이 좋다.

Bounded Context란?

![image.png](attachment:2c7c9312-055b-4fce-8164-b509221216a1:image.png)

같은 용어라도 하위 도메인마다 의미가 다르고 같은 대상이라도 지칭하는 용어가 다를 수 있다. 한 개의 모델로 모든 하위 도메인을 표현하려는 시도는 올바른 방법이 아니며 표현할 수도 없다.

하위 도메인마다 사용하는 용어가 다르기 때문에 올바른 도메인 모델을 개발하려면 하위 도메인마다 모델을 만들어야 한다.

모델은 특정한 컨텍스트하에서 완전한 의미를 갖는데, 이렇게 구분되는 경계를 갖는 컨텍스트를 DDD에서 Bounded Context라고 한다.

### 서비스 분할 기준 및 도메인 경계 설정

- **서비스 분리 기준**
    - 비즈니스 도메인과 하위 도메인 별로 서비스가 구분되어야 합니다.
    - 도메인 주도 설계(DDD)에서 강조하는 Aggregates, Entities, Value Objects 등을 활용하여 각 서비스의 경계를 명확히 합니다.
    - 데이터 일관성과 변경 주기를 고려하여, 변경이 잦은 데이터와 그렇지 않은 데이터를 분리하는 것이 좋습니다.
- **도메인 경계 정의**
    - 각 도메인은 자체 모델과 용어 체계를 갖추며, 다른 도메인과의 의존성을 최소화합니다.
    - 서비스 간 통신은 Bounded Context를 기준으로 하며, 컨텍스트 간의 통합은 명확한 계약(API, 이벤트 등)을 통해 이뤄집니다.

---

### 각 서비스별 DB 설계 원칙

- **데이터 정규화 및 스키마 설계**
    - 각 서비스는 독립적인 DB를 운영하므로, 해당 서비스에 최적화된 스키마를 구성합니다.
    - 정규화 과정을 통해 데이터 중복을 최소화하고, 필요 시 비정규화를 고려하여 성능과 확장성을 확보합니다.
- **샤딩 및 복제 전략**
    - 데이터량이 증가할 경우, 샤딩을 통해 DB 부하를 분산하고, 복제 전략을 활용해 가용성과 장애 복구 능력을 강화합니다.
    - 서비스 특성에 따라 읽기 전용 복제본과 쓰기 전용 인스턴스를 분리하는 것도 고려할 수 있습니다.
- **데이터 마이그레이션 방안**
    - 서비스 업데이트나 스키마 변경 시, 무중단 마이그레이션을 위해 버전 관리 및 단계별 마이그레이션 전략을 마련합니다.
    - 롤백 플랜을 포함하여 데이터 손실이나 장애에 대비할 수 있도록 설계합니다.

---

### Bounded Context 구체화

- **용어와 모델의 분리**
    - 각 하위 도메인은 독립적인 Bounded Context 내에서 용어와 모델을 정의합니다.
    - 동일한 용어라도 컨텍스트에 따라 다른 의미를 갖는 경우, 컨텍스트 명칭을 명시적으로 구분합니다.
- **컨텍스트 간 연결 방법**
    - 컨텍스트 간 통신은 API, 메시지 브로커 또는 이벤트 버스를 활용하여 구현합니다.
    - 데이터 연관성을 유지하기 위해 컨텍스트 간에 필요한 데이터는 동기/비동기 방식으로 교환하며, 데이터 중복 저장 시 동기화 메커니즘을 마련합니다.
- **구체적 사례 및 모델**
    - 예를 들어, 주문 서비스와 결제 서비스가 각기 다른 Bounded Context에 속할 경우, 주문 서비스에서는 주문 내역만 관리하고 결제 내역은 결제 서비스에서 관리하도록 분리합니다.
    - 이때, 주문 완료 이벤트를 발행하여 결제 서비스가 이를 수신하는 형태로 통합할 수 있습니다.

---

### 서비스 간 통신 및 데이터 일관성 전략

- **API 호출 및 이벤트 기반 통신**
    - 서비스 간 동기식 통신은 RESTful API 또는 gRPC를 통해 구현하고, 비동기식 통신은 메시지 큐나 이벤트 버스를 활용합니다.
    - 이벤트 소싱, CQRS 등의 패턴을 통해 읽기/쓰기 분리 및 데이터 일관성 유지를 고려합니다.
- **분산 트랜잭션 관리**
    - 서비스 간 트랜잭션은 Saga 패턴을 적용하여, 각 단계별 로컬 트랜잭션과 보상 트랜잭션을 통해 일관성을 관리합니다.
    - 트랜잭션 경계가 명확하지 않은 경우, eventual consistency(최종 일관성) 모델을 도입할 수 있습니다.

---

### API 게이트웨이 및 인터페이스 설계

- **API 게이트웨이 구성**
    - 외부 클라이언트와 내부 서비스 간 인터페이스를 분리하기 위해 API 게이트웨이를 두어, 인증, 로드밸런싱, 라우팅 등을 중앙에서 관리합니다.
- **인터페이스 설계 원칙**
    - RESTful API나 gRPC 등 명확한 인터페이스 표준을 적용하고, 각 서비스의 역할과 책임에 맞게 엔드포인트를 설계합니다.
    - 보안 측면에서는 인증, 인가, 암호화 등 정책을 적용하여 외부 공격 및 데이터 유출을 방지합니다.

---

### 에러 처리 및 장애 대응 전략

- **오류 상황에 대한 처리 방안**
    - 각 서비스는 자체적인 오류 처리 로직을 갖추고, 발생 가능한 예외 상황에 대해 명확한 응답 코드를 정의합니다.
- **로깅 및 모니터링**
    - 중앙 집중식 로그 수집 시스템 및 모니터링 도구를 도입하여, 서비스 상태 및 오류 상황을 실시간으로 파악할 수 있도록 합니다.
- **장애 복구 전략**
    - Circuit Breaker 패턴, 리트라이 로직, 백업 및 복구 방안을 마련하여, 서비스 장애 시 신속한 복구가 가능하도록 설계합니다.

---

### 보안 및 접근 제어

- **데이터 접근 권한 관리**
    - 각 서비스별로 접근 제어 정책을 수립하고, 역할 기반 접근 제어(RBAC)를 적용하여 불필요한 데이터 접근을 제한합니다.
- **서비스 간 보안 통신**
    - TLS 등 암호화 프로토콜을 사용하여 서비스 간 데이터 통신의 보안을 강화합니다.
- **인증 및 인가**
    - OAuth, JWT 등 표준 인증 방식을 도입하여 사용자 및 서비스의 신뢰성을 확보하며, 보안 정책을 지속적으로 점검합니다.

# Docker Compose 개요

- Docker Compose는 **여러 개의 컨테이너로 구성된 애플리케이션을 정의하고 실행하기 위한 도구**이다.
- **YAML 파일**을 사용하여 컨테이너의 설정 및 관계를 관리한다.

---

## 사용 목적

- 다중 컨테이너 환경에서 **빠른 환경 구축**과 **쉬운 관리**를 위해 사용
- 로컬 개발, 테스트, 배포 환경을 동일하게 유지할 수 있도록 지원

---

## 구성 요소 및 주요 개념

### ① docker-compose.yml 파일

- Docker Compose의 핵심으로 컨테이너 설정을 정의한다.
- 서비스(services), 네트워크(networks), 볼륨(volumes) 등을 정의한다.

**예시**

```yaml
yaml
복사편집
version: '3.8'

services:
  web:
    build: .
    ports:
      - "5000:5000"
    volumes:
      - .:/code
    depends_on:
      - redis

  redis:
    image: redis:alpine

```

### ② 서비스(services)

- 컨테이너로 실행할 개별 애플리케이션 단위
- 이미지, 포트, 볼륨, 환경변수 등을 정의할 수 있다.

### ③ 네트워크(networks)

- 서비스 간 네트워크를 정의하여 통신할 수 있게 설정
- 명시하지 않으면 기본(default) 네트워크 사용

### ④ 볼륨(volumes)

- 데이터를 컨테이너 외부에 영구적으로 저장하기 위해 사용

---

## 주요 명령어

- 구성된 서비스를 시작하고 중지하는 주요 명령어는 다음과 같다.

| 명령어 | 설명 |
| --- | --- |
| `docker compose up` | 컨테이너를 생성하고 실행 |
| `docker compose up -d` | 백그라운드에서 컨테이너 실행 |
| `docker compose down` | 컨테이너 및 관련 네트워크 중지 및 제거 |
| `docker compose build` | 서비스의 이미지 빌드 |
| `docker compose ps` | 실행 중인 컨테이너 상태 확인 |
| `docker compose logs` | 컨테이너 로그 확인 |

---

## Docker Compose 장점

- **환경 일관성 유지** 및 간편한 설정 공유
- 여러 컨테이너 관리가 쉽고 효율적
- 빠른 개발 및 테스트 환경 구축 가능

---

## 정리

Docker Compose는 여러 컨테이너 기반 애플리케이션 환경에서 설정과 실행을 편리하게 관리하는 필수적인 도구이다. YAML 파일을 통해 빠르고 간편하게 컨테이너 간 연결 및 설정을 정의할 수 있다.

# Docker 디버깅 개요

Docker 환경에서 문제가 발생했을 때, 원인을 찾고 해결하는 과정이다. 주로 컨테이너 실행, 이미지 빌드, 네트워크 문제, 볼륨 관리 등과 관련된 이슈가 발생한다.

---

## 주요 디버깅 이슈 유형

- **컨테이너 실행 오류**
- **컨테이너 상태 점검 (비정상 종료 등)**
- **이미지 빌드 실패**
- **포트 바인딩 및 네트워크 문제**
- **파일 및 볼륨 관련 문제**

---

## Docker 디버깅 방법

### ① 컨테이너 로그 확인

컨테이너가 정상적으로 실행되지 않을 때 가장 먼저 할 작업이다.

```
shell
복사편집
docker logs [컨테이너명 또는 ID]

```

- 실시간 로그 보기

```
shell
복사편집
docker logs -f [컨테이너명 또는 ID]

```

### ② 컨테이너 상태 확인

컨테이너가 실행 중인지, 혹은 종료 상태인지 확인한다.

```
shell
복사편집
docker ps -a

```

### ③ 컨테이너 내부 진입

실행 중인 컨테이너에 접속하여 내부 상태를 점검한다.

```
shell
복사편집
docker exec -it [컨테이너명 또는 ID] sh
# bash 쉘 접속
docker exec -it [컨테이너명 또는 ID] bash

```

### ④ 이미지 빌드 실패 시 디버깅

Dockerfile 빌드 중 실패할 경우 로그를 보고 원인을 파악한다.

```
shell
복사편집
docker build -t [이미지명] .

```

- 중간 단계부터 빌드하여 빠르게 오류를 찾는다. (캐시 활용)

```
shell
복사편집
docker build --no-cache -t [이미지명] .

```

### ⑤ 포트 및 네트워크 점검

포트 충돌 및 네트워크 연결 오류 시 확인

```
shell
복사편집
docker network ls
docker network inspect [네트워크명]

# 포트 확인
docker ps
netstat -anp | grep [포트번호]

```

### ⑥ 볼륨 디버깅

볼륨이 제대로 연결되지 않았거나 데이터를 찾을 수 없을 때

```
shell
복사편집
docker volume ls
docker volume inspect [볼륨명]

```

### ⑦ Docker 시스템 자원 상태 점검

Docker가 리소스 부족으로 비정상 작동할 경우를 점검한다.

```
shell
복사편집
docker stats

```

---

## 디버깅을 위한 유용한 팁

- 이미지를 빌드할 때 레이어를 최소화하면 디버깅이 쉬워진다.
- 컨테이너는 최소한의 프로세스만 실행하는 것이 디버깅에 유리하다.
- 명확한 컨테이너 명칭과 태그를 사용하면 디버깅이 편리하다.

---

## 정리

Docker 디버깅은 문제 유형에 따라 적절한 도구를 선택해 문제 원인을 신속히 찾아 해결하는 과정이다. 각종 Docker 명령어(logs, exec, inspect 등)를 적극 활용하여 빠르게 문제를 진단하고 해결할 수 있어야 한다.
