
# 도메인 주도 설계

---

## [DDD란?](https://ko.wikipedia.org/wiki/%EB%8F%84%EB%A9%94%EC%9D%B8_%EC%A3%BC%EB%8F%84_%EC%84%A4%EA%B3%84)

> 도메인 패턴을 중심에 두어, 해당 도메인에 맞게 소프트웨어를 모델링하는 설계 접근 방식이다.
> 

소프트웨어를 만들 때, 실제 업무나 문제 영역(도메인)을 깊이 이해하고 그에 맞게 프로그램을 설계하는 방식으로, 도메인의 전문가와 개발자가 함꼐 협력하여 비즈니스 로직과 규칙을 코드에 잘 반영하도록 만드는 것이다. 

## 특징

- 소프트웨어 코드는 실제 비즈니스 용어를 그대로 사용하여 구현된다. 예를 들어 대출 신청 프로그램 같은 경우, 'LoanApplication'(대출 신청서)이나 'Customer'(고객) 같은 클래스와 'AcceptOffer'(제안 수락) 또는 'Withdraw'(철회) 같은 메소드를 사용해, 코드를 비즈니스 상황과 자연스럽게 연결시킨다. **이를 언어 통일(Ubiquitious Language)라고 한다.**
- 도메인 그 자체와 도메인 로직에 초점을 맞춘다. 일반적으로 많이 사용하는 **데이터 중심의 접근법**을 탈피해서 순수한 도메인의 모델과 로직에 집중한다. 즉, 비즈니스 로직과 도메인 모델을 중심으로 시스템을 설계한다.
- [소프트웨어 엔티티와 도메인 컨셉을 가능한 일치시킨다. 분석 모델과 설계, 코드가 다른 구조가 아니라 도메인 모델부터 코드까지 항상 함께 움직이는 구조의 모델을 지향하는 것이 DDD의 핵심 원리이다.](https://incheol-jung.gitbook.io/docs/q-and-a/architecture/ddd#undefined-12)
- 도메인 전문가와 개발자 간 지속적으로 협력하며 모델을 개선하고 발전시킨다.

## 적용 상황

1. 도메인 복잡성이 높은 경우
    - 비즈니스 규칙과 로직이 복잡하고 다양한 비즈니스 용어 및 프로세스가 존재하는 경우
    - 도메인 전문가의 지식과 경험이 프로젝트 성공에 결정적인 영향을 미치는 경우
2. 비즈니스 로직이 핵심 경쟁력인 경우
    - 애플리케이션의 주요 가치가 단순한 CRUD(생성, 조회, 수정, 삭제) 이상의 복잡한 비즈니스 로직에 기반할 때
    - 도메인 모델을 통해 비즈니스 문제를 해결하는 것이 경쟁력 강화에 기여하는 경우
3. **지속적인 도메인 지식 공유와 협력이 필요한 경우**
    - 개발팀과 도메인 전문가(비즈니스 측)가 긴밀하게 협력하여 도메인 모델을 지속적으로 개선해야 하는 상황
    - 팀 내 공통 언어(Ubiquitous Language)를 통해 소통 효율성을 높일 필요가 있을 때
4. **도메인의 변화가 빈번한 경우**
    - 비즈니스 요구사항이나 시장 변화에 따라 도메인 로직 및 규칙이 자주 변할 가능성이 있는 경우
    - 모델의 확장성과 유지보수를 고려하여 설계가 중요한 경우
5. **대규모 시스템 또는 분산 시스템의 경우**
    - 시스템이 여러 모듈(혹은 Bounded Context)로 구성되어 있으며, 각 모듈 간의 경계와 통신을 명확히 할 필요가 있을 때
    - 시스템 복잡도를 낮추고, 각 도메인의 자율성을 보장하며, 일관성을 유지하는 것이 중요한 경우

### 추가 고려 사항

- **직의 역량**: DDD를 효과적으로 적용하려면 팀원들이 도메인 지식을 깊게 이해하고, 도메인 전문가와의 소통이 원활해야 한다.
- **프로젝트 규모**: 도메인의 복잡성이 낮거나 프로젝트 규모가 작을 경우 DDD의 도입이 오히려 불필요한 복잡성을 초래할 수 있다.
- **비즈니스 요구사항의 명확성**: 도메인 모델링의 핵심은 비즈니스 요구사항을 정확하게 파악하는 것이므로, 초기 요구사항 분석 단계에서 충분한 시간과 노력이 필요하다.

## 구분

### 전략적 설계 Strategic Design

- **목표:**
    
    > 전체 시스템의 큰 그림을 그리며, 도메인을 여러 부분으로 나누어 각 부분이 명확한 경계를 갖도록 하는 것이다.
    > 
- **주요 개념:**
    - **Bounded Context:**
    하나의 도메인이 여러 의미로 해석될 수 있을 때, 각기 다른 해석이나 모델을 분리하는 경계이다. 예를 들어, "고객"이라는 개념이 영업, 고객지원, 마케팅 등에서 다르게 사용될 수 있는데, 이때 각각의 영역(컨텍스트)으로 나누어 관리한다.
    - **Context Mapping:**
    여러 Bounded Context 간에 어떻게 소통하고 협력할 것인지 그 관계와 통신 방법을 정의한다.
    - **Subdomain 분류:**
    도메인을 핵심 도메인(Core Domain), 지원 도메인(Supporting Domain), 일반 도메인(Generic Domain)으로 구분하여, 각 도메인이 가진 중요도와 역할을 명확하게 한다.
    
    <aside>
    
    전략적 설계는 회사나 시스템의 전체적인 구조를 잡고, 각 팀이나 부서가 어떤 역할을 해야 하는지 큰 틀에서 정리하는 것과 비슷하다. 전체 조직도를 만들고, 각 부서의 역할과 책임을 분명히 하는 것이라고 할 수 있다.
    
    즉, 시스템 전체의 큰 그림과 도메인 간의 경계, 관계를 정의하는 단계로, '어떤 부문(컨텍스트)들이 존재하는가?'와 '각 부문은 어떻게 연결되어 있는가?'를 다룬다.
    
    </aside>
    

### 전술적 설계 Tactical Design

- **목표:**
    
    > 전략적 설계에서 정해진 도메인 경계 내에서, 실제 코드로 구현할 수 있는 도메인 모델을 만드는 데 집중한다.
    > 
- **주요 개념:**
    - **엔티티 (Entity):**
    고유한 식별자를 가지고 있으며, 시간이 지나도 본질이 유지되는 객체이다. 예를 들어, 특정 고객의 정보는 그 고객 고유의 ID를 통해 식별할 수 있다.
    - **값 객체 (Value Object):**
    고유 식별자가 없으며, 값 자체로 의미가 있는 객체이다. 예를 들어, 주소나 날짜처럼 변경 불가능한 데이터를 표현할 때 사용된다.
    - **애그리거트 (Aggregate)와 애그리거트 루트 (Aggregate Root):**
    관련 객체들을 하나의 단위로 묶어 일관성을 유지하기 위한 경계이다. 애그리거트 루트는 이 단위 내에서 중심 역할을 하며, 외부에서는 오직 루트를 통해서만 접근한다.
    - **도메인 서비스 (Domain Service):**
    특정 엔티티에 속하지 않는 비즈니스 로직을 캡슐화한다. 예를 들어, 여러 엔티티에 걸쳐서 처리해야 하는 복잡한 업무 규칙을 수행할 때 사용된다.
    - **리포지토리 (Repository):**
    도메인 객체들을 저장하고 불러오는 역할을 한다. 데이터베이스 접근 등의 영속성 관련 작업을 담당한다.
    - **팩토리 (Factory):**
    복잡한 객체 생성을 담당하여, 객체 생성 로직을 한 곳에 모아 관리한다.
    
    <aside>
    
    전술적 설계는 실제 소프트웨어 개발에서 쓰이는 도구와 같은 역할이다. 예를 들어, 건물을 짓기 전에 설계도를 그리는 전략적 설계가 있다면, 전술적 설계는 그 설계도를 바탕으로 실제 벽돌, 창문, 문 등을 구체적으로 만드는 공정이라고 할 수 있다.
    
    즉, 전략적 설계 내에서 실제 비즈니스 로직을 구현하는 방법론으로, 객체, 서비스, 데이터 접근 등 구체적인 코드 설계 방식을 다룬다.
    
    </aside>
    

## 주의 사항

- **도메인 복잡성 판단:**
    
    DDD는 복잡한 도메인 문제를 해결하는 데 강점을 발휘하지만, 도메인이 단순하거나 비즈니스 로직이 복잡하지 않다면 오히려 과도한 설계가 될 수 있다.
    
- **도메인 지식의 충분한 확보:**
    
    도메인 전문가와의 긴밀한 협력이 필수. 도메인에 대한 깊은 이해가 없다면 모델이 실제 비즈니스 요구를 제대로 반영하지 못할 수 있다.
    
- **조직 및 팀의 역량:**
    
    DDD를 성공적으로 적용하려면 팀 전체가 도메인 주도 설계의 원칙과 개념을 잘 이해해야 한다. 팀원 간의 공통 언어(Ubiquitous Language)를 정립하고 이를 지속적으로 유지하는 것이 중요하다.
    
- **경계(Bounded Context) 정의의 어려움:**
    
    도메인을 명확하게 분리하는 것은 핵심적인 작업이지만, 현실에서는 각 컨텍스트 간의 경계 설정이 쉽지 않을 수 있다. 잘못 정의하면 시스템 간의 결합도가 높아질 위험이 있다.
    
- **비용 및 시간 투자:**
    
    초기 도메인 모델링과 전략적 설계 단계에 많은 시간과 노력이 필요하며, 이는 프로젝트 초기 비용 증가로 이어질 수 있다. 프로젝트의 규모와 복잡성에 따라 적절한 투자 여부를 판단해야 한다.
    
- **기존 시스템과의 통합:**
    
    기존 시스템이나 레거시 코드와 통합할 때, DDD의 개념을 적용하기 어려울 수 있으며, 적절한 안티-코럽션 레이어 등 통합 전략을 마련해야 한다.
    
    *안티-코럽션 레이어: 
    
    안티-코럽션 레이어(ACL)는 외부 시스템이나 레거시 시스템과 내부 도메인 모델 사이의 **"번역기"** 역할을 하는 설계 패턴이다. 이를 통해 서로 다른 모델 간의 직접적인 의존성을 피하고, 내부 도메인 모델이 외부 시스템의 변화에 영향을 받지 않도록 보호할 수 있다.
    
- **일관성 유지:**
    
    전술적 설계(엔티티, 애그리거트, 도메인 서비스 등)와 전략적 설계(컨텍스트, 경계 등)가 서로 잘 맞물려야 시스템 전반의 일관성이 유지된다. 그렇지 않으면 모델이 산만해질 위험이 있다.
    

## 추가 사항

### 도메인 이벤트 Domain Event

**개념 및 역할**

- **정의:**
    
    도메인 이벤트는 시스템 내에서 비즈니스 규칙이나 프로세스에 따라 중요한 상태 변화가 발생했음을 나타내는 이벤트이다. 예를 들어, 주문이 생성되거나 결제가 완료되면 해당 이벤트를 시스템 내에서 발행한다.
    
- **느슨한 결합:**
    
    도메인 이벤트를 사용하면 이벤트를 발생시키는 컴포넌트와 이를 처리하는 컴포넌트 사이의 직접적인 의존성을 줄인다. 이벤트를 수신하는 쪽은 이벤트의 발생 사실만 인지하면 되므로, 두 컴포넌트가 독립적으로 진화할 수 있다.
    
- **비동기 처리 및 확장성:**
    
    이벤트 기반 아키텍처에서는 이벤트를 큐에 쌓아 비동기로 처리할 수 있다. 이를 통해 시스템이 높은 부하를 처리할 때 유연하게 대응할 수 있으며, 여러 컴포넌트가 이벤트를 독립적으로 처리한다.
    

**예시**

- **온라인 쇼핑몰:**
    
    고객이 주문을 완료하면 `OrderPlaced` 이벤트가 발생한다. 이 이벤트를 수신한 후에,
    
    - **재고 관리 시스템은** 주문한 상품의 재고를 감소시키거나 업데이트한다.
    - **알림 시스템은** 고객에게 주문 확인 메시지를 보낸다.
    - **배송 시스템은** 배송 준비 프로세스를 시작한다.
    
    이렇게 각 시스템이 독립적으로 이벤트에 반응함으로써, 주문 처리 과정이 모듈화되고 유지보수가 용이해진다.
    

**핵심 포인트**

- 도메인 이벤트는 시스템의 상태 전환을 명시적으로 표현한다.
- 발행자와 구독자 간의 느슨한 결합을 유지하여 시스템 확장 및 변경에 유리하다.
- 이벤트 기반 통신을 통해 비동기 처리가 가능해지며, 시스템의 반응성과 확장성이 향상된다.

### 애그리게이션 및 일관성 보장

**애그리거트의 개념**

- **애그리거트 (Aggregate):**
    
    도메인 내의 관련 객체들을 하나의 단위로 묶어 하나의 트랜잭션 단위로 관리할 수 있도록 한 모델이다. 애그리거트는 일관된 상태를 유지하며, 외부에서는 오직 **애그리거트 루트 (Aggregate Root)**를 통해서만 내부 객체에 접근한다.
    
- **애그리거트 루트:**
    
    애그리거트 내의 중심 객체로, 해당 애그리거트에 속한 모든 객체의 일관성 및 규칙을 관리한다. 예를 들어, 주문(애그리거트 루트)에는 주문 항목, 결제 정보 등이 포함되며, 외부에서는 주문 루트를 통해서만 이 정보에 접근한다.
    

**일관성 보장**

- **트랜잭션 경계 설정:**
    
    애그리거트는 트랜잭션의 경계로 작용한다. 한 애그리거트 내에서 여러 객체에 대한 변경이 발생할 때, 이를 하나의 트랜잭션으로 묶어 데이터의 일관성을 보장한다. 이를 통해 도메인 규칙이 깨지지 않고 모든 변경이 원자적으로 적용된다.
    
- **불변성 및 비즈니스 규칙 적용:**
    
    애그리거트는 내부 상태의 불변성을 유지하도록 설계된다. 애그리거트 루트는 애그리거트 전체에 대해 비즈니스 규칙을 강제하며, 변경이 외부에서 직접 이루어지지 않도록 한다.
    
- **경계 분리:**
    
    애그리거트 간에는 직접적인 데이터 변경이 발생하지 않도록 경계를 명확하게 구분한다. 각 애그리거트는 독립적인 일관성을 유지하며, 다른 애그리거트와의 관계는 도메인 이벤트나 도메인 서비스를 통해 간접적으로 조율된다.
    

**예시**

- **은행 계좌 애그리거트:**
은행 계좌(애그리거트 루트)는 입금, 출금 등의 행위를 수행하며 계좌 잔액을 관리한다.
    - 한 트랜잭션 내에서 여러 입출금이 동시에 발생할 때, 애그리거트는 계좌의 최종 잔액이 일관되게 유지되도록 보장한다.
    - 계좌 간 자금 이체는 각 계좌의 애그리거트가 독립적으로 관리되며, 이체 관련 복잡한 규칙은 도메인 이벤트나 도메인 서비스를 통해 조율된다.

**핵심 포인트**

- **애그리거트**는 도메인 모델의 일관성을 유지하기 위한 단위로, 내부 객체들이 하나의 트랜잭션 단위로 관리된다.
- 외부에서는 **애그리거트 루트**를 통해 애그리거트 내부 객체에 접근하여 데이터 변경을 통제하고 비즈니스 규칙을 적용한다.
- 이 구조는 복잡한 비즈니스 로직과 데이터 무결성을 관리하는 데 필수적이다.

package com.example.myapp.infrastructure.repository;

import com.example.myapp.domain.model.Customer;
import com.example.myapp.domain.repository.CustomerRepository;
import org.springframework.stereotype.Repository;

import java.util.HashMap;
import java.util.Map;
import java.util.Optional;

@Repository
public class CustomerRepositoryImpl implements CustomerRepository {

    // 간단한 예시를 위한 메모리 기반 저장소
    private Map<Long, Customer> database = new HashMap<>();
    private Long idSequence = 1L;

    @Override
    public Optional<Customer> findById(Long id) {
        return Optional.ofNullable(database.get(id));
    }

    @Override
    public void save(Customer customer) {
        // ID가 없으면 새로 할당
        if (customer.getId() == null) {
            customer.setId(idSequence++);
        }
        database.put(customer.getId(), customer);
    }
}

## 설명

- **도메인 계층:**
    
    비즈니스의 핵심 개념과 규칙(예: `Customer` 엔티티)을 정의한다. 저장소 인터페이스(`CustomerRepository`)도 여기에 포함되어 도메인 모델과 관련된 데이터 접근 계약을 정의한다.
    
- **애플리케이션 계층:**
    
    도메인 모델을 활용하여 사용 사례(비즈니스 로직)를 조합한다. 예를 들어, `CustomerService`는 고객 등록 로직을 수행하며 도메인 계층의 엔티티와 저장소 인터페이스를 호출한다.
    
- **인프라스트럭처 계층:**
    
    데이터베이스와 같은 외부 시스템과의 구체적 연동을 담당한다. 여기서는 메모리 기반의 간단한 구현(`CustomerRepositoryImpl`)을 예시로 들었지만, 실제 환경에서는 JPA나 MyBatis 등으로 대체할 수 있다.
    
- **인터페이스 계층:**
    
    외부에 API나 사용자 인터페이스를 제공하는 부분이다. `CustomerController`는 HTTP 요청을 받아 애플리케이션 계층의 서비스로 전달한다.
    
- **도메인 계층 (domain):**
    
    핵심 비즈니스 로직, 도메인 모델, 엔티티, 밸류 오브젝트, 도메인 이벤트 등을 포함한다. 이 계층은 비즈니스 규칙을 집중적으로 관리하며, 다른 계층에 의존하지 않아야 한다.
    
- **애플리케이션 계층 (application):**
    
    도메인 계층을 활용하여 구체적인 비즈니스 사용 사례를 구현한다. 서비스, 명령 핸들러 등이 이 계층에 위치하며, 도메인 로직을 조합해 클라이언트의 요구사항을 처리한다.
    
- **인프라스트럭처 계층 (infrastructure):**
    
    데이터베이스, 메시징 시스템, 외부 API 등 실제 시스템과의 통신 및 기술적 세부 구현을 담당한다. 도메인 계층은 이 계층에 의존하지 않고, 인터페이스(추상화)를 통해서만 상호작용하게 된다.
    
- **인터페이스 계층 (interfaces):**
    
    외부에 제공하는 API나 UI, 그리고 클라이언트와의 통신을 담당한다. REST API, 웹소켓, UI 컨트롤러 등이 포함된다.
    

이와 같이 폴더명을 나누는 이유:

1. **관심사의 분리 (Separation of Concerns):**
    
    각 계층이 자신의 책임에만 집중하도록 하여 코드의 복잡도를 낮추고, 유지보수성을 높인다.
    
2. **응집력 강화 (Cohesion):**
    
    동일한 목적과 역할을 가진 클래스들을 한 곳에 모아둠으로써, 관련 코드들이 자연스럽게 함께 유지되고 이해하기 쉬워진다.
    
3. **의존성 관리 (Dependency Management):**
    
    핵심 비즈니스 로직(도메인 계층)이 외부 인프라스트럭처나 인터페이스의 변화에 영향을 받지 않도록 격리하여, 변경에 유연하게 대응할 수 있다.
    
4. **확장성과 테스트 용이성:**
    
    각 계층이 분리되어 있기 때문에 새로운 기능 추가나 테스트 작성 시 독립적으로 작업할 수 있으며, 모듈 간 결합도를 낮춰 확장하기 좋다.

## Docker State

**개념 및 역할**  
Docker 컨테이너의 상태는 해당 컨테이너가 현재 어떤 실행 상태에 있는지를 나타내며, 애플리케이션의 라이프사이클 관리 및 문제 해결에 중요한 역할을 합니다.

**주요 상태**

- **created**  
  컨테이너가 생성되었지만 아직 실행되지 않은 상태입니다.
  
- **running**  
  컨테이너가 정상적으로 실행되고 있는 상태입니다.
  
- **paused**  
  `docker pause` 명령어로 컨테이너의 모든 프로세스를 일시 중지한 상태입니다.
  
- **exited**  
  컨테이너 내의 프로세스가 종료되었으나, 컨테이너 자체는 삭제되지 않은 상태입니다.
  
- **restarting**  
  자동 재시작 정책(`--restart`)에 따라 컨테이너가 재시작 중인 상태입니다.
  
- **dead**  
  심각한 문제로 인해 Docker 데몬에서 컨테이너를 더 이상 제어할 수 없는 상태입니다.

**핵심 포인트**

- `docker ps -a` 명령어로 모든 컨테이너와 해당 상태를 확인할 수 있습니다.
- 상태 전이는 애플리케이션의 실행 및 장애 상황을 파악하는 데 중요한 정보를 제공합니다.
- 자동 재시작 정책(`--restart`)을 설정하면, 컨테이너가 예기치 않게 종료되었을 때 자동으로 복구할 수 있어 서비스 안정성이 향상됩니다.
- 컨테이너 상태를 모니터링하고 로그를 분석함으로써, 문제 발생 시 빠른 대응이 가능해집니다.

**추가 고려 사항**

- **로그와 모니터링:**  
  Docker 컨테이너의 상태뿐만 아니라 로그 파일(예: `docker logs <컨테이너명>`)을 주기적으로 모니터링하여, 애플리케이션의 이상 징후를 조기에 발견할 수 있습니다.
  
- **상태 관리 도구:**  
  Prometheus, Grafana 등 모니터링 도구를 사용하면 컨테이너의 상태와 자원 사용량을 실시간으로 확인할 수 있어 운영자가 시스템 전체의 건강 상태를 파악하는 데 도움을 줍니다.

## Docker Volume

**개념 및 역할**  
Docker Volume은 컨테이너의 데이터를 호스트 시스템과 분리하여 영속적으로 저장할 수 있도록 하는 메커니즘입니다.  
컨테이너가 삭제되거나 재시작되더라도 볼륨에 저장된 데이터는 유지되므로, 데이터 무손실이 중요한 애플리케이션(예: 데이터베이스, 로그 저장 등)에서 필수적으로 사용됩니다.

**볼륨 종류**

1. **Anonymous Volume (익명 볼륨)**  
   - `docker run -v /app/data`와 같이 컨테이너 경로만 지정하면, Docker가 임의의 이름으로 익명 볼륨을 생성합니다.
   - 이름이 지정되지 않으므로 관리 및 추적이 어려울 수 있으며, 컨테이너 삭제 후에도 남아 있을 수 있어 주기적인 정리가 필요합니다.

2. **Named Volume (이름 있는 볼륨)**  
   - `docker volume create my-volume` 또는 `docker run -v my-volume:/app/data`와 같이 명시적으로 이름을 지정하는 방식입니다.
   - `docker volume ls` 명령어로 목록 확인이 가능하며, 재사용 및 관리가 용이합니다.
   - 이름 있는 볼륨은 여러 컨테이너 간에 데이터를 공유할 때도 유용합니다.

3. **Bind Mount (바인드 마운트)**  
   - `docker run -v /host/path:/app/data`처럼 호스트의 특정 디렉토리를 컨테이너의 경로에 직접 연결하는 방식입니다.
   - 개발 환경에서는 코드 변경 사항을 실시간 반영하거나 로컬 파일 시스템을 그대로 사용하기에 편리합니다.
   - 운영 환경에서는 호스트의 권한, 보안, 파일 시스템 구조에 직접 의존하므로 신중하게 사용해야 합니다.

**사용 예시**

```bash
# 1. 이름 있는 볼륨 생성
docker volume create my-volume

# 2. 이름 있는 볼륨을 사용하여 MySQL 컨테이너 실행
docker run -d \
  --name my-mysql-container \
  -v my-volume:/var/lib/mysql \
  mysql:8.0
